**Decision 2026-08-11 (product owner, SPEC-CONFLICT #281, F-101 create replay):** APPROVED option 1. Every `POST /api/events` carries a UUID `Idempotency-Key`. The first accepted request atomically stores that key and its exact JSON intake body with the event. A replay with the same key and body returns the original event before current intake validation; a replay with a different body is refused with 409 and writes nothing. A missing or malformed key is refused with 400 and writes nothing. Migration 015 adds nullable `create_idempotency_key` and `create_request_body` columns for compatibility with historical rows, pairs them with a check constraint, and uniquely indexes every non-null key; the API requires both on every new create. The browser retains the original key, body, and answers in per-tab session storage across a form remount or reload after an outcome it did not observe, sends that immutable retry before applying current client validation or starting another create, and clears recovery only after initial planning has a known stored-or-not-stored outcome. It then continues the already approved first-plan flow from the returned event ID. Because the pre-key and keyed web/api builds cannot safely mix for this request, the one-time migration-015 rollout denies organizer traffic to both services until both builds and an end-to-end synthetic create check succeed, as `DEPLOY.md` specifies. This closes the lost-response gap without moving plan generation server-side and changes no engine behavior, ruleset, regulatory content, finding, verdict, deadline, fee, portal, or verification status. Approval is in the product, API, architecture, database, affected-lane, and all-lane capacities named by governance §6; the product owner currently holds each capacity, so this is one approval in those capacities rather than independent sign-offs.

This #281 approval is for the current access-gated synthetic-data demo. It does not satisfy or relax the strict production ratification gate recorded for the shared `events` contract.

**Artifact checksums:** the current ruleset row above carries a `sha256` digest, per `ARCHITECTURE-FUTURE.md` §14 step 5, which requires a published artifact to carry version, checksum, changelog and approval metadata before this manifest is updated. The digest is **SHA-256 over the exact bytes of the file at the path in that row**, with nothing normalised, no key reordering and no whitespace stripped, so it is reproducible with one command and depends on nothing but the file:

```
sha256sum rules/nyc-rules.v2.13.json
```

It lives here rather than inside the artifact because a digest stored in the file it covers would change the bytes it describes. `pnpm check:baseline` recomputes it and fails on a mismatch, so a ruleset edited without republishing, or a row left pointing at a digest that no longer matches, breaks the build rather than going unnoticed. Stating the algorithm and the coverage is the point: a checksum whose derivation is not written down cannot be verified by anyone later.
