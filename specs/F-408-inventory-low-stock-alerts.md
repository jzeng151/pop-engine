# F-408 · Inventory Low-Stock Alerts

**Status:** PROPOSED (2026-07-26) — ready for review; not implementable until approved and listed in `docs/BASELINE.md`.

**Phase:** 4 · **Issue:** [#56](https://github.com/jzeng151/pop-engine/issues/56) · **Owner:** TBD · **Reviewer:** product owner · **Approval date:** —

## Purpose and User Outcome

Event staff can maintain manual item counts and receive deterministic low-stock warnings; an optional Square webhook may update counts only after a separate provider decision.

## Scope

**In scope**

- Create event inventory items, record manual count adjustments with reason, set a nonnegative alert threshold, and show/send low-stock transitions.
- Optionally ingest approved Square inventory events through a verified idempotent adapter.
- Preserve adjustment/source history and distinguish stale provider state.

**Non-goals**

- POS, payments, sales analytics, purchasing, forecasting, recipes, multi-location inventory, or generic Square integration.
- Treating an unverified webhook as inventory truth.

## Inputs, Outputs, State, Validation, and Errors

- Inputs are item, integer adjustment/current count, threshold, source, and a stable request identity on item creation, on each manual adjustment, and on each absolute count or threshold set; outputs are append-only adjustments and derived current/low-stock state.
- Low-stock transition occurs when known count becomes at or below threshold; unknown/stale count is separate and never reported healthy.
- Duplicate provider events are idempotent; out-of-order events follow the approved cursor/version policy.
- Missing or unresolved material data stays visibly unset, unknown, pending, or failed as appropriate; it never becomes a successful or complete result.
- Invalid input produces a field or action-specific error without partial mutation. Retriable external failures preserve the user's confirmed state and expose a safe retry.

## UI and Accessibility

- Staff controls show current count, threshold, source freshness, adjustment history, and non-color low/unknown/stale warnings.
- The complete workflow is keyboard operable, uses programmatic labels and visible focus, does not encode status by color alone, and announces asynchronous success or failure.
- Empty, loading, permission-denied, validation, provider-failure, and unavailable states have explicit copy and a safe next action.

## Acceptance Criteria

1. **F408-AC-01:** Manual integer adjustments bind a stable operation identity to actor/time/reason/source history, deterministically derive current count, and return the original result without reapplying on replay. That identity is committed with the adjustment under a uniqueness constraint scoped to the inventory item it mutates, which is the scope the later statement of this criterion already assumes when F408-AC-09 records that this identity "is scoped to adjustments of an item that already exists". A deliberate second adjustment of a different item, or of the same item, sends a new identity and is applied normally.

   The scope is stated because leaving it to the implementation makes two legitimate adjustments collide. Under a global or event-wide key, a staff member adjusting two items in one action, or two staff members adjusting different items of one event, can present one identity against different operands, and F411-AC-08's operand binding then refuses the second as a mismatched reuse rather than recording it, so a real stock change is lost with a conflict the staff member cannot act on. Under an implementation-chosen key, replay behaves differently from one item to the next and no fixture can state what a retry should return. Scoping to the item makes the identity mean what AC-09 already says it means: one adjustment of one existing item. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. The acting actor's current authority is not among the checks the identity is resolved past: the authority this feature requires for a first attempt is re-read server-side at the replay, and the stored outcome is returned only if it still admits the operation, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.

2. **F408-AC-02:** Creating an item with a known count at/below its threshold, first resolving an unknown/stale count to known at/below, or changing a known item from above threshold to at/below creates one low-stock transition/alert; the reverse known-low to known-above change records one recovery transition. Initialization above threshold creates no transition. Notification jobs pin the item generation, deliver in generation order after rechecking it, and suppress a stale low-stock alert after recovery; retries/repeated reads do not duplicate either transition or notification.
3. **F408-AC-03:** Unknown or stale count is labeled and cannot appear in-stock.
4. **F408-AC-04:** Invalid, replayed, duplicate, out-of-scope, or unverified Square events cannot change inventory.
5. **F408-AC-05:** The provider connection requests no payment capability and no feature surface performs POS, purchasing, or forecasting.
6. **F408-AC-06:** For distinct verified Square events delivered out of order, the approved provider cursor/version ordering rejects or records the delayed older event without allowing it to regress current count, freshness, or low-stock state.
7. **F408-AC-07:** Disconnect and verified-event application compete on the same mapping version/lock; event application atomically verifies the active mapping and mutates inventory, while a winning disconnect prevents that mutation and all later provider events. Provider-derived inventory becomes stale or unavailable while manual counts remain usable.

   Disconnect is itself a durable mutation of the mapping and not only a fence over the event application, so it names the exact mapping version it reviewed, commits only by compare-and-swap on that version, and carries a stable client-supplied request identity committed in that same transaction under a uniqueness constraint scoped to the mapping. That identity binds its operands under `F411-AC-08`, which are the event, the mapping, and the reviewed version, and a presented identity that already holds a committed disconnect is resolved from that record before the version comparison, on the ordering `F411-AC-08` states once for every client-supplied identity on this branch, returning that disconnect's recorded outcome and disconnecting nothing a second time. `F212-AC-04` states this shape in full and this criterion requires it on the same terms. Without both halves a disconnect composed for one mapping version and retried after the organizer has reconnected tears down the mapping they just established, and a retry the comparison refuses reports a disconnect that committed as stale.

8. **F408-AC-08:** An operation that SETS an absolute value — a current count or a threshold — names the exact item generation it was composed against and commits only by compare-and-swap on it; an operation naming a superseded generation is rejected, changes no count, threshold, freshness, or low-stock state, and returns the current item for the staff member to recompose against. An identity makes a replay safe but does not make a stale value correct, so two tabs composing distinct absolute values from one observed state are both valid without this comparison and the delayed one overwrites the newer count and spuriously creates or reverses a low-stock transition under F408-AC-02. F408-AC-01's identity is not that identity in any case, because it is scoped to adjustments of an item that already exists, which is why each set carries its own below. Append-only delta adjustments carry no such generation and continue to accumulate independently in any order.
   Each absolute SET, of a current count and of a threshold alike, also carries its own stable client-supplied request identity, committed with the set in that same transaction under a uniqueness constraint scoped to the inventory item it sets, distinct from every other set's and from the adjustment identity F408-AC-01 defines. A recognized replay returns the outcome that set originally recorded, including the low-stock or recovery transition F408-AC-02 derived from it, and sets nothing a second time. The acting actor's current authority is not one of the checks that identity is resolved past: the authority that admits a first attempt, membership and permission where an organizer acts and the equivalent admission where the caller is a public or door client, is re-read server-side at the replay, and the stored outcome is returned only if it still admits the request, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch, which here are the item, the exact absolute value being set, whether it is a count or a threshold, and the item generation the request named, so a reuse presenting a different value is refused as a conflict and sets nothing. It is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: the identity is resolved before the item-generation compare-and-swap above, because the commit the retry repeats is exactly what advanced the generation that comparison reads. A set whose identity resolves to no committed outcome is then held to that comparison, and one refused by it commits no identity, so re-presenting it later is a first set and not a replay.

   An absolute SET needs its own identity for a reason a delta adjustment does not, and the sentence above about a stable operation identity making a replay safe is what has to be corrected: F408-AC-01's identity is scoped to adjustments of an item that already exists, as F408-AC-09 records, so no absolute set has ever had one, and the fixture list proves replay only for adjustments. Nor is a set harmless to replay simply because it is absolute rather than a delta. Re-applying `+5` twice is visibly wrong and re-applying `count = 12` twice looks like it converges, which is exactly why the gap survived, but two things break that reading. The first is that this criterion's compare-and-swap makes the retry fail rather than converge: the retry names the item generation the staff member was composed against, which the original set advanced, so it is rejected, changes nothing, and returns the current item for them to recompose against. A committed set is reported to the person who made it as stale, on an event-day surface whose whole purpose is to keep a count trustworthy, and the recomposition they are sent to do is against a value they cannot distinguish from someone else's write. The second is that the value is idempotent and the history is not. Between the original set and its retry, an append-only delta adjustment under F408-AC-01 can legitimately commit; re-applying the absolute value on top of it silently discards that adjustment, regresses the count this criterion says a superseded generation may not regress, and creates or reverses a low-stock transition under F408-AC-02 that no real stock movement caused. A replayed absolute set is therefore not a no-op with respect to anything F408-AC-02 or F408-AC-03 report, which is the whole reason the generation comparison exists, and the identity is what lets the retry be recognized instead of being answered by either failure.

9. **F408-AC-09:** Item creation carries its own client-generated request identity, and the transaction that creates the item commits that identity under a uniqueness constraint scoped to the event, so a retry after a lost response returns the original item and its F408-AC-02 transition result instead of creating a second item and a second low-stock alert. F408-AC-01's operation identity does not reach this case: it is scoped to adjustments of an item that already exists. A deliberate second item sends a new identity. Uniqueness over item name or recorded attributes is not that enforcement: an event may legitimately stock two items whose recorded attributes are identical, so it would refuse a real item. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. The acting actor's current authority is not among the checks the identity is resolved past: the authority this feature requires for a first attempt is re-read server-side at the replay, and the stored outcome is returned only if it still admits the operation, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.
10. **F408-AC-10:** When the optional Square path is enabled, starting provider authorization issues a single-use callback state that the server stores bound to the initiating actor, the workspace, the provider, and the exact approved redirect target, on the same terms `F212-AC-06` states in full and `F702-AC-10` requires of every externally initiated callback. The callback rejects any request whose state is missing, unrecognized, expired, already consumed, or bound to a different actor, workspace, provider, or redirect; a rejection stores no credential and creates no connection or mapping, and a successful callback retires its state. AC-07's disconnect invalidates every outstanding state issued against the prior mapping generation, so a delayed callback cannot recreate the mapping after disconnect.

    AC-04 and AC-06 govern what a verified provider event may do once a mapping exists, and AC-07 governs disconnecting one, so nothing today constrains how the mapping came to exist. An attacker who begins authorization against their own Square account and induces a staff member to open the callback binds that attacker's account to the staff member's workspace; every later event then arrives verified under AC-04, passes the active-mapping check in AC-07, and moves that workspace's counts, so AC-03's freshness labelling reports attacker-chosen numbers as known. State entropy and lifetime are not established by any approved artifact today; they belong to the provider ADR named in the Approval Blockers, so until that approval names them this criterion is testable only as "an unguessable single-use state is required, bound, verified, and consumed before credentials are stored, and disconnect invalidates every outstanding state," not against a specific length or expiry. The manual path this feature ships first establishes no connection and is unaffected.

11. **F408-AC-11:** Every staff operation this feature defines names the inventory item or event it acts in and the workspace that owns it, and is admitted only by the acting actor's current F-702 membership of that workspace together with the F-703 permission approved for the action, both re-read server-side from stored membership and role at the moment of the operation and, for a write, inside the same transaction that commits it. That covers manual count adjustments under F408-AC-01, absolute count and threshold sets under F408-AC-08, item creation under F408-AC-09, provider disconnect under F408-AC-07, starting provider authorization under F408-AC-10, and every read of current count, threshold, source freshness, and adjustment history under F408-AC-03 and the staff controls named under UI and Accessibility. This criterion and F408-AC-10 compose as `F212-AC-07` composes with `F212-AC-06`: at authorization start this criterion admits the actor before AC-10 mints any callback state, so a state is only ever bound to an initiating actor who held the permission at issuance, and at the callback AC-10's binding, single-use, and generation checks run first and this criterion then re-reads the actor's current membership and permission before any credential is stored, so authority withdrawn between issuance and callback fails the callback with no credential stored and no mapping created. Square webhook ingestion under F408-AC-04 and F408-AC-06 is deliberately excluded: it is provider-initiated and carries no acting user, and it is bound by the stored mapping it names and by signature and timestamp verification, not by this criterion. A request failing the check is refused before any durable write and before any count, threshold, freshness state, or adjustment history is disclosed, and its response does not distinguish an item or event that does not exist from one the actor may not see. The check is at the operation and not at session start or workspace switch, so authority removed while a request is in flight causes that request to fail rather than commit.

    **The same boundary binds the mapping a provider event is applied through, not only the item or event the request names.** A Square mapping names a provider inventory object and a local inventory item, and the mapping, that provider object, and that item must all resolve to one event, the event whose count the mapping moves, and to the workspace that owns it. The comparison is made server-side when a mapping is created or changed, inside the transaction that commits it, and again inside the transaction F408-AC-07 uses to apply a verified provider event, before any count, freshness state, or low-stock transition moves. A mapping whose provider object and local item do not resolve to the same event is refused at creation and applies nothing at ingestion, and the refusal does not distinguish an item that does not exist from one the mapping may not target. F408-AC-10's callback state is bound to that event as well as to the initiating actor, workspace, provider, and redirect, so a state issued while one event was selected cannot establish a mapping into another.

    F408-AC-07 verifies that the selected mapping is active, and nothing verifies what it points at. An organizer who can act in two events of one workspace holds a real membership and a real permission for both, so every actor check this criterion makes passes; the mapping exists and is active; the provider object belongs to the connected Square account. What no criterion asks is whether the item the mapping moves is in the event the operation named. A mapping created or selected for event B against event A's item makes every later authentic Square webhook change A's count under F408-AC-04 and F408-AC-06 and raise or clear A's low-stock alerts under F408-AC-02, with no invalid, replayed, duplicate, out-of-scope, or unverified event anywhere in the path, so F408-AC-04 has nothing to refuse and F408-AC-03 labels the attacker-chosen numbers known. The workspace comparison does not reach it, because one workspace holds many events. This is the case F702-AC-10's fourth obligation describes: the mapping and the item are named together and never compared, and AC-07's compare-and-swap on the mapping version proves the mapping is current without proving it belongs here.

    Without this criterion F408-AC-01 through F408-AC-10 all pass for an authenticated caller who names another workspace's event or item. They fix operation identity, transition and notification behavior, freshness labelling, provider-event verification, ordering, disconnect concurrency, absolute-set compare-and-swap, creation identity, and callback-state binding, and not one asks whether the actor may act at all: F408-AC-10 binds a state to whoever initiated it without admitting that initiator, so even the provider connection can be started, and under F408-AC-07 disconnected, against a workspace the actor holds no membership of, and every count, threshold, and adjustment history is readable and every manual write is committable by anyone who can name the item or event.

    One input this criterion needs is not established by any approved artifact today and is not invented here. F-703 is PROPOSED and names no role set, so the permission above cannot be named. Until F-703 is approved this criterion is testable only as "every manual inventory write and every inventory disclosure is refused unless the acting actor holds an active membership of the workspace that owns the named event or item, read server-side at that operation, and a refusal discloses nothing about whether that item or event exists", not against a named role or permission identifier. Naming the inventory read, adjustment, item-creation, absolute-set, and provider-connection permissions with F-703 is an approval blocker below.

## Fixtures and Verification

- Planned automated fixture IDs are the acceptance IDs above; each must map one-to-one to a runnable test before approval can claim implementation readiness.
