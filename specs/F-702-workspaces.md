# F-702 · Workspaces

**Status:** PROPOSED (2026-07-26) — ready for review; not implementable until approved and listed in `docs/BASELINE.md`.

**Phase:** 2 · **Issue:** [#49](https://github.com/jzeng151/pop-engine/issues/49) · **Owner:** TBD · **Reviewer:** product owner · **Approval date:** —

## Purpose and User Outcome

Authenticated organizers can group events and members inside an explicit workspace boundary so one organization's data cannot leak into another.

## Scope

**In scope**

- Create, name, view, and switch workspaces; manage membership invitations and acceptance.
- Derive workspace scope server-side for every authenticated aggregate.
- Require workspace ownership before authenticated user-owned product data is persisted.

**Non-goals**

- Role-specific permissions beyond the minimum owner needed to establish a workspace; F-703 owns authorization roles.
- Workspace billing, domains, SSO, nested organizations, or cross-workspace sharing.

## Dependencies and Baseline

- F-701 authentication.
- The F-701/F-702/F-703 joint production gate in `ROADMAP.md` and `ARCHITECTURE-FUTURE.md` §15.2.
- Baseline at draft time: PRD, Roadmap, Design, and Phase 0–1.5 Architecture approved 2026-07-22; `ARCHITECTURE-FUTURE.md` approved as a planning target 2026-07-25; NYC ruleset `nyc.v2.7`, rules schema `popengine-rules/v2`, and scenario fixtures v5 where regulatory output is consumed.
- Operand binding and replay ordering for client-supplied identities are stated locally in `F702-AC-12` and are deliberately not declared as a dependency on `specs/F-411-staff-roles-credentialed-entry.md`. Other specs on this branch take that rule by reference to `F411-AC-08`, but F-702 cannot: F-411 already declares F-702 as a dependency, because `F411-AC-09` admits every organizer-side operation by the workspace membership boundary this spec defines, so declaring F-411 here would make the two specs blockers of each other and neither could be approved first. The phase order says the same thing from the other side, since F-702 is the Phase 2 workspace gate and F-411 is a Phase 3 spec, so a Phase 2 gate cannot wait on it. F-703 met the identical cycle and resolved it the same way in `F703-AC-03`. Which rule belongs where is what decides the direction: the membership boundary is this spec's own subject and F-411 genuinely consumes it, while the identity rule is about client-supplied identities on durable writes and is not about door credentials, which `F411-AC-08` itself records. Restating it locally is therefore the option taken, and it leaves no unapproved undeclared input in any criterion below. If the rule is later promoted to an approved shared invariant, this spec, F-703, and F-411 all cite that invariant and the local restatements are removed.
- The approval PR must re-pin any baseline version that changes before approval. A proposed or superseded input blocks implementation.

## Inputs, Outputs, State, Validation, and Errors

- Inputs are an authenticated actor, workspace name, and invitation target; outputs are a workspace, membership, and server-selected active workspace context.
- Invitation states and every transition between them, including who may perform each one and against which identity and version, are enumerated in F702-AC-08. Membership state is active → removed. Membership transitions, including who may perform each one and against whom, are enumerated in F702-AC-11; no transition may leave the workspace without an active owner.
- A client-supplied workspace identifier is never sufficient authorization; every aggregate query joins through active membership.
- Missing or unresolved material data stays visibly unset, unknown, pending, or failed as appropriate; it never becomes a successful or complete result.
- Invalid input produces a field or action-specific error without partial mutation. Retriable external failures preserve the user's confirmed state and expose a safe retry.

## UI and Accessibility

- Workspace switcher and invitation screens identify the active workspace before any mutation and clearly distinguish expired, revoked, and unauthorized invitations.
- The complete workflow is keyboard operable, uses programmatic labels and visible focus, does not encode status by color alone, and announces asynchronous success or failure.
- Empty, loading, permission-denied, validation, provider-failure, and unavailable states have explicit copy and a safe next action.

## Acceptance Criteria

1. **F702-AC-01:** Workspace creation and active-owner membership insertion are atomic and bind a stable client-supplied request identity to the original result; replay returns that workspace and membership without creating another. That identity is committed under a uniqueness constraint scoped to the creating actor, not to a workspace, because the workspace it would be scoped to is what this operation creates. This is the one mutation F702-AC-10 does not reach, and F702-AC-11 M-00 is the membership transition it performs. That identity binds its operands under the rule `F702-AC-12` states once for every client-supplied identity this spec defines: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F702-AC-12` states once for every client-supplied identity this spec defines, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. The acting actor's current authority is not among the checks the identity is resolved past: the authority this feature requires for a first attempt is re-read server-side at the replay, and the stored outcome is returned only if it still admits the operation, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.
2. **F702-AC-02:** Acceptance atomically compare-and-swaps the invitation from pending to accepted together with membership creation; revocation competes on the same row/version, so exactly one terminal transition wins. Expired, revoked, reused, or mismatched invitations create no membership. "Mismatched" is defined by F702-AC-08 as the accepting actor's verified identity failing to equal the invitation's recorded target identity, and that comparison is made inside this same transaction, before membership creation.
3. **F702-AC-03:** Every workspace-owned aggregate rejects cross-workspace reads, writes, identifier guessing, exports, uploads, and job execution.
4. **F702-AC-04:** Owner removal/leave serializes on the workspace (or uses an equivalent database invariant) so the last active owner cannot be removed under concurrent requests; the concurrent two-owner removal fixture leaves at least one owner. This criterion decides only that the invariant survives concurrency; who may perform each membership transition, and against whom, is F702-AC-11, and the authority check it names is made inside this same serialized transaction.
5. **F702-AC-05:** No authenticated user-owned product data or external beta is enabled before F-703 is also deployed and verified.
6. **F702-AC-06:** Issuing and revoking an invitation require the actor to hold an active owner membership of that exact workspace, checked server-side against stored membership rather than any client-supplied workspace or role claim. A non-owner member, a removed member, and a member of a different workspace are each rejected without disclosing whether the workspace or invitation exists, and the rejection creates, mutates, and expires nothing.

   This is the minimum owner authority the non-goals reserve to F-702 rather than a role model, which stays F-703's. Without it, AC-02 and AC-03 hold and the boundary still opens: AC-02 governs only transitions of an invitation that already exists, and AC-03 admits anyone who reached active membership. An ordinary member could therefore invite an outsider, the outsider would accept through AC-02 into a valid membership, and every cross-workspace check in AC-03 would pass for them, because by then they are legitimately inside. Membership is what AC-03 trusts, so the criterion that decides who may create membership cannot be deferred to F-703 while F-702 ships. Revocation is named alongside issuance for the same reason: leaving it open lets any member cancel an owner's pending invitation.

7. **F702-AC-07:** Issuing an invitation binds the request to a stable client-supplied request identity, committed with the invitation under a uniqueness constraint scoped to the workspace. A retry presenting the same identity returns the original invitation and its original token and creates no second pending row; deliberately inviting the same address again sends a new identity. This is request identity, never content uniqueness: two genuinely distinct invitations that read the same are both created, and a repeated identity is never rejected as a duplicate value. That identity binds its operands under the rule `F702-AC-12` states once for every client-supplied identity this spec defines: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F702-AC-12` states once for every client-supplied identity this spec defines, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. The acting actor's current authority is not among the checks the identity is resolved past: the authority this feature requires for a first attempt is re-read server-side at the replay, and the stored outcome is returned only if it still admits the operation, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.

   AC-02 serializes transitions of one invitation and cannot see a second one. When issuance commits and its response is lost, the caller retries, a second pending row and a second token exist for the same intended invitation, and revoking or accepting either leaves the other still valid, so a revocation the owner was told succeeded does not close the invitation.

8. **F702-AC-08:** An invitation has exactly the states and transitions in the table below, and no operation outside that table creates, changes, or ends an invitation or a membership derived from one. An invitation is in exactly one of `absent` (no record), `pending`, `accepted`, `revoked`, or `expired`; the last three are terminal, and no transition leaves a terminal state. Issuance records, immutably and at creation, the normalized intended target identity the invitation is for; that recorded target is never re-supplied by a later request and never changed after issuance. Every transition names the invitation version it read and compare-and-swaps that version inside the transaction that performs it.

   T-11 exists because T-05 and T-07 otherwise disagree about one request. When an acceptance commits and its response is lost, the retry presents the same token and the same verified actor, but the invitation it names is now `accepted` rather than `pending`, so T-07 rejects it as reused or invalid while the membership T-05 created is live. The accepting actor is told their invitation was already used or is no longer valid, by the same operation that in fact admitted them, and the only recoveries left are asking an owner for a second invitation under T-01, which issues a second pending row for someone who is already a member, or reading the membership through a workspace surface F702-AC-03 will not show them until they know they are inside it. Resolving the acceptance identity before the state comparison is the ordering `F702-AC-12` states once for every client-supplied identity this spec defines, applied here rather than restated: the state check T-07 makes cannot distinguish a retry from a genuine reuse, because the commit the retry repeats is exactly what made the state terminal. The verified-identity comparison is not skipped and is not what the identity replaces: a presented identity whose actor does not equal the recorded target is refused on T-06's terms and returns nothing about the stored acceptance, and an identity whose operands, the invitation and the accepting actor, do not match what was committed with it is refused as a conflict under `F702-AC-12` rather than answered. A retry that carries no such identity is an ordinary T-07 refusal, and the terminal `accepted` state stays a terminal state for every actor other than the one whose acceptance produced it.

   T-12 exists for the same reason on the other side of the same row, and until now revocation was the one transition in this table that changed an invitation and committed no identity of its own. T-01 issuance has the F702-AC-07 identity and T-05 acceptance has its own, so a revocation whose response is lost is the only invitation write whose retry has nothing to resolve against. That retry names the `pending` invitation and the version the owner read, both of which its own commit moved: the state is now `revoked` and terminal, so the transition finds no `pending` row to leave, and the version comparison finds the version already advanced. The owner is told the invitation was not pending, or that their revocation was stale, by the operation that in fact revoked it, at the moment they are trying to establish that a pending invitation is closed. The plausible next action, revoking again, is indistinguishable from a first revocation of an invitation someone else already revoked, so it does not settle the question either. Resolving the revocation identity before the state and version comparison is the ordering `F702-AC-12` states once for every client-supplied identity this spec defines, applied here rather than restated, and it grants nothing the original revocation was not granted: the owner-membership check T-08 requires is still made on that record's terms before anything is returned, so an actor who no longer holds an active owner membership is refused rather than answered, and an identity whose operands, the workspace and the invitation it named, do not match what was committed with it is refused as a conflict under `F702-AC-12` and revokes nothing. A retry carrying no committed identity against an invitation that is already `revoked` is an ordinary refusal on this table's terms, exactly as T-07 is for acceptance.

   Each earlier round on this spec secured one step of this lifecycle and left the next, which is why the whole set is enumerated here rather than another rule being added beside them. F702-AC-06 fixed who may issue and revoke. F702-AC-07 fixed issuance replay. F702-AC-02 fixed the race between accepting and revoking one invitation that already exists. None of the three said who may accept: acceptance was reached by presenting the token, so the token was a bearer credential for entering the workspace, and a forwarded, leaked, or stolen one admitted whoever held it. Once inside, F702-AC-03 passes for that membership because it is a real membership, exactly as F702-AC-06 already described for an invitation issued by a non-owner. Delivery and expiry had no criterion at all: nothing said the delivery adapter may send only to the recorded target, so an implementation could accept a delivery address from the caller and bypass the binding T-05 checks, and nothing said an expired invitation is terminal at the moment of use, so an implementation could depend on a sweep the System Impact says workspace consistency must not depend on.

   Two inputs this criterion needs are not established by any approved artifact today, and both belong to the invitation decisions already named in the Approval Blockers. First, the normalization rule for the target identity: it must be one approved deterministic rule applied identically at T-01 and T-05 and recorded with the invitation, and it must be conservative, because a rule that folds distinct addresses onto one normalized target widens the set of actors T-05 admits. Second, the invitation lifetime T-09 measures against. Until that approval names them, T-01, T-05, and T-09 are testable only as "a single recorded normalized target is compared for equality at acceptance, and a configured finite lifetime is enforced at every use," not against a specific rule or window. This criterion also requires F-701's actor projection to report whether the actor's email is verified, which F701-AC-05 does not state today: it exposes the verified subject and an optional email without saying the email is verified as owned. Where that verification state is unavailable, T-05 fails closed and no membership is created, because admitting an unverified identity would restore the bearer behavior this criterion removes.

9. **F702-AC-09:** Switching the active workspace names one target workspace. The server accepts the switch only when the actor holds an active membership of that exact workspace and the workspace itself is active, both checked server-side against stored membership rather than any client-supplied workspace or role claim. On success the server-selected active workspace context becomes that workspace, and every subsequent read and mutation derives its scope from the new context, so the switcher reaches each workspace the actor is actually a member of instead of remaining pinned to the first one. A target the actor is not an active member of, whose membership was removed, or that is not active is rejected without disclosing whether the workspace or the membership exists, and the previously active context is left unchanged.

   Switching selects among authority the actor already holds; it never creates, restores, or elevates any. It is not itself an authorization decision beyond the membership check above, and the authority for each later operation is still that actor's stored membership of the now-active workspace, re-read server-side per request rather than carried forward from the previously active workspace or frozen into the session at switch time. Being an owner of one workspace therefore confers nothing in another, a membership removed after a switch takes effect on the next request, and F702-AC-03 still rejects every request naming an aggregate outside the active workspace, so the active context narrows what a request may reach and never widens it. This is stated because the same identity-scoping defect has already appeared once on this stack: an operation that resolved authority from something other than the actor's own stored membership of the exact target. A switch that returned a context the server then trusted in place of a per-request membership check would be that defect again, with the client choosing the scope.

10. **F702-AC-10:** This criterion governs operations performed _inside_ an existing workspace: every mutation of a workspace-owned aggregate, and every externally initiated callback, whose authority is the actor's stored membership of that workspace. Each such operation names the workspace it acts in. That named workspace is validated against the actor's authority at the moment of the write, re-read server-side from stored membership rather than from the session, from a client-supplied role claim, or from the context that was active when the operation began. Switching the active workspace never retroactively changes what an in-flight operation acts on: an operation that named workspace A commits in workspace A or is rejected, and never in workspace B.

    Two operations fall outside that scope by definition rather than by exception, because in each one the actor holds no membership to validate at the moment of the write, and each is governed by the criterion named beside it instead. **Workspace creation**, F702-AC-01, is the operation that brings the workspace and its first membership into existence, so there is no prior workspace for the request to name and no stored membership to check; its authority is F-701 authentication alone, and its replay identity is scoped to the creating actor rather than to a workspace, since no workspace exists to scope it to. **Invitation acceptance**, F702-AC-08 T-05, acts in a workspace the accepting actor is by definition not yet a member of; the workspace it acts in is the one recorded on the invitation server-side and is never supplied or chosen by the client, and its authority is the comparison of the actor's F-701 verified identity against the immutable recorded target, made before any membership row is written. Neither operation may be read as permission to write a workspace-owned aggregate without a membership check: creation writes only the workspace and its founding owner membership, acceptance writes only the membership, and every write either performs afterwards is inside this criterion's scope again.

    The scope sentence is stated first because the earlier wording, "every mutation," reached the bootstrap it cannot apply to. Workspace creation could then satisfy the tenancy rule only by inventing a client-selected workspace identifier and an authorization path this spec does not define, and invitation acceptance could satisfy it only by finding a membership that acceptance is what creates. A rule that forbids a legal operation is a defect exactly as much as one that permits an unsafe operation, so the scope is fixed here rather than an exception list being bolted beside the rule.

    This is the tenancy boundary rule for the whole feature set, stated once here and referenced rather than restated wherever a workspace-scoped operation or an external callback needs it. Four obligations follow from it, and an implementation satisfies the criterion only by meeting all four.

    First, naming. Every request that writes carries the workspace it was composed against, and every externally initiated callback carries a server-issued reference that resolves to one workspace. Naming is not authorization: the named workspace only narrows what the request may reach, and the actor's stored membership of that exact workspace is what admits it, exactly as F702-AC-09 already requires of a switch. A request whose named workspace differs from the server-selected active context is rejected and returned for the actor to recompose, and is never silently redirected into the currently active workspace. The rejection discloses nothing about whether the named workspace or its aggregates exist, per F702-AC-03.

    Second, validation at the moment of the write. The membership check is made inside the transaction that commits, against stored membership read server-side at that instant, not at session start, not at switch time, and not at the moment the client began composing. A membership removed while a request was in flight therefore causes that request to fail rather than commit on authority the actor no longer holds.

    Third, callbacks. An externally initiated callback is not composed by the actor at all, so it cannot carry the actor's current context. Its workspace binding is instead established when the flow starts: the server issues and stores an unguessable single-use state bound to the initiating actor, the workspace, the provider, and the exact approved redirect target, and the callback is admitted only when it presents that state, which is consumed exactly once. `F212-AC-06` states this shape in full and `F308-AC-11` and `F408-AC-10` require it by reference; a callback with no such binding acts in whatever workspace the browser session happens to be in, which is the attacker-chosen workspace whenever the attacker started the flow.

    Fourth, co-tenancy of everything the request names. An operation that names more than one record requires every record it names to resolve to the same workspace, compared server-side inside the transaction that commits the operation and, for a read, at the operation that returns a value derived from any of them. The three obligations above are all about the actor: they ask where the actor stands and whether that authority is current. This one is about the objects, and it is the direction the actor check cannot see, because an actor holding an active membership of workspace A and an active membership of workspace B does nothing they are not entitled to do in either place separately while pairing a record from one with a record from the other. Every check written on the actor therefore passes, every named record genuinely exists, and the result of the operation carries one workspace's data into the other's.

    The obligation covers every record the request supplies independently of the aggregate the authority criterion binds, whatever the spec calls it: another aggregate, a pinned version or generation, a source document, a selected recipient or contact snapshot, a subject membership, a run or proposal set, and a target the operation is about to create. It is not satisfied by a check that the named record exists, by a compare-and-swap proving the named version is current, or by a request identity whose operands include it, because a record in another workspace exists, its version is current there, and the operands match what was committed. A mismatch rejects the whole operation before any durable write, mutates nothing, appends no history, projection, generation, job, or audit entry, discloses no field of any named record, and returns a response that does not distinguish a record that does not exist from one that resolves to a different workspace, per F702-AC-03.

    The records the request supplies are not all the records the comparison covers. An operation also reaches records it never names, through the records it does: a channel endpoint through the contact it belongs to, a provider object through the mapping that targets it, a prior artifact through the lineage it sits in, an approval or a run through the artifact it was granted against. Those are operands of the operation as much as the named ones, because they are what the write finally lands on, and no reading of a criterion's own prose can enumerate them, since the criterion does not mention them. Each of them is compared to its own immediate parent, and through that parent to the scope above, so the chain is closed rather than each link being tied separately to a common ancestor: binding two records to one event does not make one of them a record of the other. The comparison is made wherever the operation acts, which for a deferred operation is at every point it acts: when a set is assembled or a mapping selected, again inside the transaction that commits, and again immediately before each provider call, job execution, or delivery, because the relationship can be true at one of those and false at the next.

    A scope stored beside a record is not the comparison either, and this is the direction that is easiest to miss. Where a record carries a workspace, jurisdiction, or event as a column rather than reaching one through a parent, that column is derived from the record it scopes inside the transaction that writes it, not supplied alongside it and validated on its own. A row written with an aggregate from one scope and a scope value from another satisfies every requirement that both fields be present and name something real, and it is then filtered on the value that is wrong: it appears where it does not belong, or a defensive read-time comparison hides it from both places and leaves the owning scope's history incomplete with no criterion permitting a repair.

    Where a spec's own aggregate is narrower than a workspace, the comparison is made at that narrower scope as well, not instead. The event is that scope throughout this feature set: one workspace holds many events, so two records in one workspace satisfy the workspace comparison while belonging to different events, and a spec whose aggregate is an event compares the event and the workspace both. `F406-AC-09` and `F407-AC-08` state the pair that way, and `F105-AC-08`, `F214-AC-09`, `F604-AC-09`, `F502-AC-08`, and `F503-AC-07` state the workspace half for the records they name.

    The scope of each comparison is set by the slot that consumes the record, not by the widest scope the feature legitimately spans. Reading "the narrowest aggregate this spec owns" as the feature's span is what leaves a multi-event, multi-contact, or multi-milestone feature fenced at the workspace and nothing narrower, and the reasoning looks sound at each site because a fence at the span's own aggregate really would break the feature: an event fence makes a cross-event analytics refresh, a cross-event comparison, a workspace-wide contact export, and a workspace-wide calendar connection uncomputable for exactly the records they exist to show. The conclusion drawn from that is the error. A span says which records may be gathered and never says which one a gathered record may stand in for. Every value a gathered record supplies still lands in one slot, one comparison column, one exported row, one provider entry, one replaced current pointer, and the comparison is against the record that owns that slot: the event whose column consumes a snapshot, the contact whose row consumes a consent version, the milestone whose sync consumes a mapping. That comparison is available to a spanning feature exactly as it is to a single-aggregate one, because the slot exists either way.

    A criterion is read leg by leg for this, not as a whole. Where one leg resolves a record through its owner and another lets the caller name the record directly, only the first leg carries the comparison, and it carries it incidentally rather than by being required to. A per-event current pointer, a per-contact current version, a per-milestone existing mapping each land in the right slot because the lookup started from the owner; the explicit-selection, historical-version, or caller-supplied alternative beside them starts from the record instead and must state the comparison the default leg never had to. The correctly bound default is what makes the unbound alternative invisible to a reader checking whether the criterion binds its records, so the leg that lets a caller name a record is the one to read.

    This obligation is stated here because it has been found one instance at a time for several rounds and each instance was closed by restating the same sentence in another spec. Nine criteria now say it locally, and each carries its own harm paragraph and its own approval blocker. That is the same cost `F702-AC-12` records for the client-supplied-identity rule and for the same cause: the rule has no approved home, so a spec that needs it cannot reference one. The obligation stated here is what those criteria are applications of, and what a spec that has not yet been read for it inherits. It does not make them removable today. F-702 is `PROPOSED`, so a reference to this criterion is not an approved input and a spec whose implementation is built from its own criteria still needs the rule in words it owns; `F411-AC-08` and `F702-AC-12` additionally cannot reference each other at all, because F-411 declares F-702 a dependency and the reverse edge would make the two blockers of each other. Collapsing every local restatement into a reference to this obligation becomes correct when F-702 is approved and listed in `docs/BASELINE.md`, and is recorded as an approval blocker below rather than done now.

    Without this criterion, F702-AC-03 and F702-AC-09 both hold and the boundary still opens. F702-AC-03 rejects cross-workspace access by comparing an existing aggregate's workspace to the active one, so it has nothing to compare for a create, which has no aggregate yet, and the actor is legitimately a member of both workspaces so no membership check fails. F702-AC-09 then makes the active context mutable without giving any subsequent request a way to say which context it was composed against. A member with workspace A open in one tab and workspace B in another therefore switches to B and the next create from the A tab, composed entirely against A and showing A's name in the switcher F702-AC-09 requires, writes into B. Nothing rejects it, nothing records that it was misdirected, and one organizer's data is now in another organizer's workspace. The same reasoning covers an external callback, where the gap is wider still because the party that chooses when the callback arrives is outside the boundary.

    Operations that are not workspace-scoped do not satisfy this criterion by naming a workspace. The platform rules-admin surfaces F-711 and F-712 define name their own platform scope, which `F703-AC-04` keeps separate from and ungrantable by a workspace owner, and `F711-AC-06` already states why a workspace-scoped identity would be wrong for them. Such an operation is in scope for this criterion only in that it must name a scope and validate authority for that scope at the moment of the write; the scope it names is the platform one.

11. **F702-AC-11:** Membership has exactly the transitions in the table below, and no operation outside that table creates, ends, or changes the authority of a membership. Every transition except M-00 reads the acting actor's own stored membership of that exact workspace server-side, inside the same serialized transaction F702-AC-04 requires, never from a session, a client-supplied workspace, or a client-supplied role claim. M-00 is the bootstrap and is the one transition for which no such membership can exist to be read, for the reason F702-AC-10 gives: it is the transition that creates the first one. M-07 is the replay, and it reads that membership like every other transition rather than being excused from it: what its row states is that the identity is resolved before the version and state comparisons M-05 and M-06 make, not before the membership read, and the single case in which the membership read cannot fail it is the M-06 self-leave whose own commit removed that membership. Reading it is what keeps a replay from returning an outcome to an actor whose membership someone else ended after the commit; resolving the identity before the state comparisons is what keeps a self-leave's retry from being denied for work that already succeeded. Both are stated in the table rather than as exceptions beside it, so the one transition that reads no membership stays visible next to the six that must. A transition whose "must remain true afterwards" column would be violated at commit is rejected in full, changes nothing, and discloses nothing about whether the workspace or the subject membership exists, per F702-AC-03.

It is listed rather than exempted so that the one transition with no membership to read is visible next to the six that must read one.

    Each earlier round on this spec closed one hole in this authority model and left the next, which is why the whole set is enumerated here rather than another rule being added beside them. F702-AC-01 fixed ownership at creation and its replay. F702-AC-06 fixed who may issue and revoke. F702-AC-07 fixed issuance replay. F702-AC-08 T-05 fixed who may accept. F702-AC-04 fixed only that the last-owner invariant survives concurrency, and said nothing about who may perform a removal, while T-10 delegated the whole removal and leave transition back to it. Removal is the most damaging of these, because an ordinary member who can remove others can remove every owner up to the last one and then hold a workspace the owners can no longer administer, and because F702-AC-03 admits whoever holds an active membership, so nothing downstream rejects the survivor.

    The table shows a fifth hole nobody has reported, and M-04 states it. The last-owner invariant is written over removal and leave, so it is evaded by a transition that ends ownership without ending membership: demote the last active owner to an ordinary member and the workspace has no owner, no membership was removed, F702-AC-04 never applies, and every criterion above still holds. Nobody can then issue an invitation under F702-AC-06, revoke one under T-08, or remove anyone under M-05, and no criterion in this spec restores ownership. F-702 cannot fix this by defining a role model, because its non-goals reserve that to F-703; what it can do, and what M-04 does, is bind the invariant to any transition that ends an actor's owner authority rather than to the removal verb, so F-703's role change inherits it instead of routing around it.

    Two inputs this criterion needs are not established by any approved artifact today. F-703 is `PROPOSED` and names no role set, so M-04 is testable only as "no transition may leave the workspace without an active owner," not against a named role or a named demotion operation, and it becomes fully testable when F-703 is approved and enumerates the transitions that end owner authority. There is also no approved recovery path for a workspace that reaches zero active owners through any route this criterion does not cover, such as the deletion of the last owner's F-701 account; this spec does not invent one, and until the tenancy and invitation decisions in the Approval Blockers name it, M-04 and M-06 prevent the state rather than repair it.

12. **F702-AC-12:** Every client-supplied request identity this spec defines is committed together with the operands that determine the result recorded under it, and a reuse that does not match those operands is a conflict and not a replay. The operands are the request fields the recorded result depends on, at minimum the workspace or the creating actor the identity is scoped to, the aggregate the request names, and every version, generation, and state the request names. A request presenting a committed identity is a replay, and receives the stored outcome, only when every one of those operands equals what was stored with it. When any of them differs, the request is refused as a conflict: it receives no stored outcome, commits nothing, creates or changes no workspace, invitation, or membership, and is neither treated as a replay nor allowed to proceed as a fresh operation under that identity. The refusal names the conflict without disclosing the stored operation's workspace, invitation, target, subject, or outcome, per F702-AC-03's non-disclosure rule, and the caller recovers by sending a new identity for the operation it actually intends. This is not content uniqueness: the identity stays the key the client chooses and the operands are only a precondition on reusing it, so two genuinely distinct operations that read the same are both committed under two identities, while one identity can only ever mean one operation. Without it, an identity is a replay key the client controls and the server honors for operands it never computed the outcome against, and returning a stored outcome for different operands is a way to make one operation masquerade as another rather than a form of idempotency.

    A committed identity is resolved before any version, generation, state, or limit check whose answer the committed operation itself changed. The identity is looked up first, against the record the committing transaction wrote; only a request whose identity resolves to no committed outcome is then evaluated against the checks that guard a first attempt, and only a request passing those is admitted and commits its outcome and identity together. A state check made first cannot tell a retry from a fresh request, because the commit the retry is repeating is exactly what moved the state that check reads: the version it names has been advanced by that commit, the pending state it requires has become terminal, or the membership that commit itself removed is gone. Every one of those rejects work that in fact succeeded and reports a completed operation to its caller as stale, conflicting, or invalid.

    The acting actor's current authority is not one of the checks the identity is resolved past, and this spec states that separately because the two rules read alike and only one of them is about state the commit moved. Every transition in F702-AC-11 and F702-AC-08 reads the acting actor's own stored membership of that exact workspace server-side at the operation, and a replay is an operation: the membership that admits a first attempt is re-read at the replay, inside the same serialized transaction F702-AC-04 requires, and the stored outcome is returned only if it still admits the request. A replay presented after that membership is gone is refused and discloses nothing about whether the workspace, invitation, or subject membership exists, per F702-AC-03. The one exception is the authority the committed operation itself removed, which is what M-07 is for: a self-leave under M-06 ends the acting actor's own membership, so that commit satisfies the read rather than failing it, and the replay returns the recorded outcome. An operation whose commit did not remove the acting actor's own membership has no such exception, so an owner whose membership was ended by someone else between the commit and the retry is refused rather than answered from the record. Without the separation, the replay guarantee would quietly outrank F702-AC-11's membership rule: a removed actor resending a committed identity would receive a result the membership read would now refuse, and the same content the fresh request is denied would come back as a retry.

    Resolving the identity first weakens none of the state checks, because a resolved identity returns exactly the outcome that was already computed under all of them, is returned only after the current-authority re-read above, and grants nothing the actor may not have at the moment of the replay; an unresolved identity is admitted only by passing every one of them, and a resolved identity whose operands do not match is refused as a conflict under the paragraph above rather than admitted to either path. The rule is directional and the consequence in the other direction is stated rather than left implied: a request refused by one of those checks commits no identity, so re-presenting it later is a first attempt and not a replay, and every replay guarantee in this spec covers exactly the identities that reached a committed outcome. F702-AC-01 applies it to workspace creation, F702-AC-07 to invitation issuance, F702-AC-08 T-11 to an acceptance whose replay a not-pending check would reject and T-12 to a revocation whose replay the same check would reject, and F702-AC-11 M-07 to a self-leave whose replay a membership precheck would deny.

    This rule is stated here in full rather than by reference to `F411-AC-08`, which states the same rule once for the specs that depend on F-411, and `F703-AC-03` states it locally for the same reason F-703 gives. The Dependencies and Baseline section explains why this spec cannot take that reference: F-411 declares F-702 as a dependency, so a dependency in the other direction would make the two specs blockers of each other and neither could be approved first. The rule is not about workspaces any more than it is about door credentials, so stating it in three places is a cost of it having no approved home rather than a design. Promoting it to an approved shared invariant covering every client-supplied identity in the system is a durable architecture decision under `docs/DOCUMENTATION-GOVERNANCE.md` §6 and needs its own ADR approval, which this spec does not have and does not take; the Approval Blockers record it as the path that removes all three restatements.

13. **F702-AC-13:** An actor holds at most one active membership of a workspace at any time. The invariant is enforced by a database uniqueness constraint over the actor and the workspace, restricted to active memberships so that a membership already `removed` under F702-AC-11 M-05 or M-06 does not block a later re-invitation, and it is checked inside the same serialized transaction F702-AC-04 requires. Acceptance under F702-AC-08 T-05 and F702-AC-11 M-02 therefore does not create a second membership for an actor who is already an active member of that workspace: it returns the existing active membership as the outcome of the acceptance and marks the invitation `accepted`, changing no role and creating no row, or it refuses without creating one. Either resolution satisfies this criterion and the choice between them is an approval decision named below, because the first leaves the recorded target with the authority they already hold and the second tells an owner their invitation was not needed; what neither may do is produce a second active row.

    This is a cardinality rule and not a tenancy one, and it is stated separately because the workspace boundary rules above are all satisfied while it is violated. T-01 deliberately permits an owner to issue another invitation to the same recorded target identity with a new request identity, since F702-AC-07's identity is a retry key and not content uniqueness, and re-inviting someone is a legitimate action when the first invitation was lost, expired, or revoked. Nothing in T-05 then compares the accepting actor against the memberships that already exist: the verified identity matches the recorded target, the invitation is `pending`, the acceptance identity is fresh, and M-02's "must remain true afterwards" column requires exactly one active membership _for that invitation_, which two rows created by two invitations each satisfy on their own.

    The harm is that every downstream rule on this branch reads "an active membership" and finds one. F702-AC-03 admits the holder of any active membership, and F702-AC-10's actor check re-reads stored membership and finds a live row. So removal under M-05, leave under M-06, and role change under M-04 each act on one row and leave the other untouched and active: an owner who removes a member sees the removal commit and the audit entry written, and the actor keeps the access the owner believes was withdrawn, through the row the removal did not name. M-07's replay makes the same mistake safely idempotent rather than visible. The count invariants are also read per row, so a demotion under M-04 can be reported as ending an actor's ownership while a second active owner membership for the same actor still stands.

    Two consequences are stated rather than left implied. First, the F702-AC-04 last-active-owner invariant counts distinct actors holding active owner memberships and not active owner rows, so two rows for one actor are one owner for the purpose of the check that a workspace is never left without one; with this criterion in force the two cannot coexist, and the counting rule is stated because an implementation that enforces uniqueness by cleanup rather than by constraint would otherwise let a transient duplicate satisfy it. Second, the constraint is what enforces this and not an application-level read-then-write, for the reason F208-AC-01 gives for its own slot: two concurrent acceptances of two invitations to the same target each read no existing membership and each insert one.

    One input this criterion needs is not established by any approved artifact today and is not invented here. Which of the two resolutions above an acceptance takes, whether the actor's role is the invited one or the one they already hold when those differ, and whether a re-invitation to a current member may be issued at all under T-01, are invitation decisions the Approval Blockers already gather, and this criterion adds them there rather than choosing. Until that approval names them this criterion is testable only as "no actor ever holds two active memberships of one workspace, and an acceptance by an actor who already holds one creates no second membership and changes no role," not against a named resolution.
