# F-711 · Rules Admin: Source Manager

**Status:** PROPOSED (2026-07-26) — ready for review; not implementable until approved and listed in `docs/BASELINE.md`.

**Phase:** 4 · **Issue:** [#64](https://github.com/jzeng151/pop-engine/issues/64) · **Owner:** TBD · **Reviewer:** product owner plus affected architecture, contract, security, and lane owners (TBD) · **Approval date:** —

## Purpose and User Outcome

The verification team can manage source metadata, bounded excerpts, archives, and link health as evidence while keeping verification decisions human-owned.

## Scope

**In scope**

- Create/version source records with URL, agency/title, retrieval metadata, bounded excerpt, archive reference, and link-check history.
- Link sources to draft/published rule facets and surface broken/unavailable changes for review.
- Restrict verification-status changes to the verification owner.

**Non-goals**

- Declaring a source authoritative automatically, copying entire copyrighted pages, editing rules, broad crawling, or silently replacing a source.
- Treating link health as regulatory validity.

## Inputs, Outputs, State, Validation, and Errors

- Inputs are human-reviewed metadata/excerpt/archive; output is a versioned source record and link-check observations.
- Source records carry only metadata, archival, and link-health lifecycle state. Regulatory verification exists exclusively on immutable rule-source facet decisions for exact artifact versions.
- A metadata correction versions the record or appends history and never rewrites evidence used by a published artifact.
- Missing or unresolved material data stays visibly unset, unknown, pending, or failed as appropriate; it never becomes a successful or complete result.
- Invalid input produces a field or action-specific error without partial mutation. Retriable external failures preserve the user's confirmed state and expose a safe retry.

## UI and Accessibility

- Source detail distinguishes facet-level verification decisions, link health, archive availability, excerpt, linked rules, history, and reviewer authority.
- The complete workflow is keyboard operable, uses programmatic labels and visible focus, does not encode status by color alone, and announces asynchronous success or failure.
- Empty, loading, permission-denied, validation, provider-failure, and unavailable states have explicit copy and a safe next action.

## Acceptance Criteria

1. **F711-AC-01:** Every source record preserves URL, agency/title, retrieval metadata, bounded excerpt/archive reference, author/reviewer, and version history.
2. **F711-AC-02:** Only the verification owner can record a review decision for an exact immutable rule-source facet and artifact version, with evidence/reason; source rows have no aggregate regulatory status, and decisions affect runtime only through publication. Decisions stay immutable, but each rule-source facet and artifact version carries exactly one current decision, identified by a current-decision generation that the recording transaction compares and swaps. Recording names the generation the author was shown; a mismatch rejects the whole write and returns the current decision, so two tabs produce one recorded decision and one rejection the author re-reviews rather than two decisions with no defined order. Superseding a decision marks the prior one superseded in that same transaction, and it stays readable as history. Readiness and publication accept only the exact current unsuperseded decision for the facet and version they read: `F710-AC-04` names the generation it evaluated and rejects on a mismatch, which is what stops it from pinning an older favorable decision after a newer one records `OFFICIAL_CONFLICT` or `RESEARCH_REQUIRED` and lets F-714 publish against stale verification evidence.
   Recording a decision, and superseding one, each carry a stable client-supplied request identity, committed in the same transaction as the immutable decision and the supersession it records, under a uniqueness constraint scoped to the rule-source facet and artifact version the decision is for, together with the recording verification owner and on the platform scope F711-AC-06 establishes rather than a tenant workspace. A supersession carries its own identity, distinct from the identity of the decision it supersedes, because superseding is itself a decision this criterion records. A recognized replay returns the decision that request originally recorded, records no second decision, marks nothing superseded a second time, and leaves the current-decision generation where that commit left it. That identity is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the current-decision generation comparison this criterion requires, because the commit the retry repeats is exactly what advanced the generation that comparison reads. A request whose identity resolves to no committed outcome is then held to that comparison, and one refused by it commits no identity, so re-presenting it later is a first recording and not a replay.

   This is not the plain retry-safety the cancellations elsewhere on this branch need, and two things make it different. The first is what a mismatched reuse would mean. A decision is a regulatory judgment a named human made, and F-710 readiness and F-714 publication accept only the exact current unsuperseded decision for the facet and version they read, so a stored outcome returned for operands the server never evaluated it against would report to the caller that the system holds a verification judgment nobody recorded. The operands committed with the identity are therefore the exact rule-source facet, the exact artifact version, the decision value, the evidence and reason recorded with it, the current-decision generation the request named, and the recording verification owner, and a reuse differing in any of them is refused as a conflict under `F411-AC-08` rather than answered: it records nothing, supersedes nothing, and returns nothing about the stored decision. Answering it would be a way to attribute one person's verification decision to another request, which `docs/DOCUMENTATION-GOVERNANCE.md` §2 and AGENTS.md's rule that only the verification owner changes verification statuses both forbid, and which no amount of idempotency makes safe.

   The second is that the identity may not stand in for authority. F711-AC-07 re-reads the acting actor's current authority server-side inside the transaction that compares and swaps the generation, and that re-read still runs on a replay, before anything is returned: a replay presented by an actor who does not currently hold the verification-owner authority is refused on that criterion's terms, and its refusal discloses nothing about the stored decision, so resolving the identity first weakens no check and returns only the outcome that was already computed under all of them. What the identity does change is nothing about regulatory content: it establishes no fact, promotes no source, and alters no decision. It removes one failure mode of the recording operation. Without it, this criterion has only the compare-and-swap, and a compare-and-swap cannot tell a retry from a stale request, because the retry names the current-decision generation the author was shown and its own commit advanced. The whole write is then rejected and the current decision returned, which is the response this criterion defines for two tabs, so the verification owner is told to re-review a decision they already recorded. Re-reviewing and recording again is the plausible next action, and it produces a second decision that supersedes their own identical first one: the facet's history gains a supersession that reflects no change of judgment, and the exact current decision F-710 and F-714 pin moves for a reason no reviewer can reconstruct.

3. **F711-AC-03:** Broken, blocked, redirected, or unavailable links create health observations and never automatically invalidate or verify a rule.
4. **F711-AC-04:** Published artifacts continue to reference immutable source versions even after metadata correction.
5. **F711-AC-05:** Fetching cannot access private network targets, unsupported protocols, unbounded content, or execute remote content.
6. **F711-AC-06:** Creating a source record, and appending a version to one, each bind the request to a stable client-supplied request identity, committed with the row under a uniqueness constraint scoped to the source for a version and, for a new source, to the platform source catalog the record is created in (its jurisdiction partition where the catalog is partitioned by one), together with the recording rules-admin actor. No part of that scope is a tenant workspace: F-711 defines platform rules-admin operations, F-703's deny-by-default state rule says platform rules-admin checks never derive from a workspace role while `F703-AC-04` keeps the rules-admin role separate from and ungrantable by a workspace owner, so a workspace-scoped identity would fail to recognise the original creation for an administrator with no active workspace or one retrying after switching workspaces, and a second global source record would be created. A retry presenting the same identity returns the original source or version and writes no second row; a deliberately separate source or a genuine new version uses a new identity. This is request identity, never content uniqueness: the same URL can legitimately be registered as two sources and re-retrieved into two versions with identical bytes, so neither URL nor content may serve as the key, and a repeated identity is never rejected as a duplicate value. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, authority, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.

   Correcting a source record's metadata and initiating a link-check job each bind their own stable client-supplied request identity on the same terms, committed in the transaction that records the correction or enqueues the job, under a uniqueness constraint scoped to the source record the correction amends or the link-check names, together with the recording rules-admin actor and on the same platform scope as above rather than a tenant workspace. A request presenting an already committed identity returns the correction or the job the original request produced, appending no second correction to the history AC-01 preserves and enqueuing no second fetch or check for one administrator action. F711-AC-07 admits these two as durable rules-admin writes, and the identity above covers only creation and version append, so without their own identities a retry after a lost response has nothing to resolve: the correction history AC-04 says published artifacts keep referring past gains a duplicate entry for one edit, and one link-check action becomes two fetches of an external agency URL, which is exactly the traffic F711-AC-05's bounds exist to keep deliberate. Each identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch: a correction's identity is committed with the source record and the corrected field values, a link-check identity with the source record and version it checks, and a reuse carrying any different operand is refused as a conflict rather than being answered with the stored result. This is request identity, never content uniqueness: the same field may legitimately be corrected twice to the same value and one source may legitimately be checked repeatedly, so neither the corrected values nor the target may serve as the key.

   AC-01 requires version history and says nothing about how a version comes to exist. When a create commits and its response is lost, the retry produces either two source identities for one document or two indistinguishable versions of one source. Rule links and the AC-02 review decisions then split across them: a decision recorded against one version leaves the other unreviewed, and F-710 readiness and F-714 publication read whichever version their pin happens to name.

7. **F711-AC-07:** Creating a source record, appending a version to one, correcting metadata, initiating a link-check job, and every read of a source detail, version, history, link-health observation, or linked-rule view are rules-admin functions and are admitted only by the separate platform rules-admin role, on the terms `F703-AC-04` states for every such function rather than on a second formulation stated here. The acting actor's current platform authority is read server-side at each read and, for each of those writes, inside the same transaction that commits it, never from the session or a client-supplied role claim, and never derived from a workspace role, per F-703's deny-by-default state rule and the separation `F703-AC-04` keeps, which is the reading F711-AC-06 already takes for its identity scope, so naming a workspace, holding any workspace role, or owning a workspace admits nothing here. F711-AC-02 remains the rule for recording a review decision, which only the verification owner performs; this criterion adds to that leg only the re-read, so the verification owner's current authority is read server-side inside the same transaction that compares and swaps the current-decision generation, and authority revoked between reading a facet and recording the decision composed from it fails the write rather than committing it. A refusal writes no row, starts no job, records no decision, and returns no source, version, history, or link-health data, and its response does not distinguish a source the actor may not see from one that does not exist, so authority revoked while any listed write is in flight fails that write rather than committing it.

   F711-AC-01 through F711-AC-06 pass for an ordinary workspace member everywhere except the verification-owner leg F711-AC-02 keeps. They say what a record preserves, what link health may not imply, what fetching may not reach, and how an identity binds a create, and F711-AC-06 names the recording rules-admin actor only inside its identity scope, which records who created a row without gating who may. The separate roles were otherwise written in the System Impact privacy row, which creates no acceptance criterion, so an implementation built to the criteria could let any authenticated user register sources into the platform catalog, start allow-listed link-check jobs, and read every archived excerpt, retrieval history, and pending facet decision.

   F-703 is PROPOSED and is not listed in `docs/BASELINE.md`, so until it is approved this criterion is testable only as "every source create, version append, metadata correction, link-check initiation, and read is refused unless the acting actor holds the separate platform rules-admin role, read server-side at that operation and, for a write, inside the transaction that commits it, and a refusal discloses nothing about what exists", not against a named role identifier, matrix entry, or grant path, which F-703's own approval blockers reserve. The verification-owner authority F711-AC-02 relies on is a separate approval named in the blockers below and is not what this criterion establishes.

## Fixtures and Verification

- Planned automated fixture IDs are the acceptance IDs above; each must map one-to-one to a runnable test before approval can claim implementation readiness.
- F711-AC-02 includes a fixture in which a review decision commits, its response is lost, and the retry presenting the same decision identity and the pre-recording current-decision generation returns the decision that request originally recorded rather than a generation-mismatch rejection, recording no second decision and marking nothing superseded a second time; the same fixture for a supersession; a mismatched-reuse fixture in which a committed decision identity is re-presented with a different decision value, evidence, facet, or artifact version and is refused as a conflict, recording nothing and returning nothing about the stored decision; and a fixture in which that committed identity is presented by an actor who no longer holds the verification-owner authority and is refused under F711-AC-07 rather than answered.
- F711-AC-06 includes a metadata-correction fixture and a link-check-initiation fixture in which the write commits, its response is lost, and the retry presenting the same identity returns the correction or the job the original request produced, appending no second correction entry and enqueuing no second fetch or check, plus a mismatched-reuse fixture in which a committed correction identity is re-presented with different field values and is refused as a conflict, recording nothing.
- F711-AC-07 includes a negative fixture per operation in which an authenticated actor holding no platform rules-admin role, including a workspace owner, is refused a source create, a version append, a metadata correction, a link-check initiation, and each read, with no row written, no job started, and a response indistinguishable from the one for a source that does not exist; a fixture in which the role is revoked between reading a source and the version append composed from it, so the write is refused at commit; and a fixture in which the verification owner's authority is revoked between reading a facet and recording its decision under F711-AC-02, so the decision is refused at commit rather than committing.
- Security-sensitive and cross-workspace paths require negative authorization tests; provider paths require success, duplicate-delivery, retry, invalid-signature, and permanent-failure tests where applicable.
