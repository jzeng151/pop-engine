# F-107 · Save and Resume

**Status:** PROPOSED (2026-07-26) — ready for review; not implementable until approved and listed in `docs/BASELINE.md`.

**Phase:** 2 · **Issue:** [#16](https://github.com/jzeng151/pop-engine/issues/16) · **Owner:** TBD · **Reviewer:** product owner · **Approval date:** —

## Purpose and User Outcome

An organizer can safely leave an incomplete intake and resume it later without fabricating answers or accidentally evaluating an unfinished event.

## Scope

**In scope**

- Persist partial F-101 answers for the authenticated workspace as immutable incomplete Event Revisions and restore the latest saved revision.
- Show completion and validation state without treating unanswered material fields as false.
- Save complete revisions that are eligible for normal F-201 evaluation without adding a separate submission transition.

**Non-goals**

- Anonymous cross-device recovery, collaborative simultaneous editing, autosuggested answers, or offline editing.
- Generating a permit plan from an incomplete draft.

## Dependencies and Baseline

- F-101 intake and the F-701/F-702/F-703 production gate. F-702 supplies the workspace membership boundary an Event and its revisions resolve against and F-703 supplies the permission matrix `F107-AC-11` checks; F-701 supplies the authenticated actor both read from. F-701 is APPROVED (2026-07-28, `docs/BASELINE.md`); F-702 and F-703 remain PROPOSED, so the gate is not an approved input today and this spec is not implementable against it until those two are approved and listed in `docs/BASELINE.md`.
- The approved `docs/EVENT-REVISION-CONTRACT.md` is authoritative; this proposal reconciles SPEC-CONFLICT #213 to that contract.
- Baseline at draft time: PRD, Roadmap, Design, and Phase 0–1.5 Architecture approved 2026-07-22; `ARCHITECTURE-FUTURE.md` approved as a planning target 2026-07-25; NYC ruleset `nyc.v2.7`, rules schema `popengine-rules/v2`, and scenario fixtures v5 where regulatory output is consumed.
- The approval PR must re-pin any baseline version that changes before approval. A proposed or superseded input blocks implementation.

## Inputs, Outputs, State, Validation, and Errors

- Inputs are partial intake values, exact registry/version, validated `base_revision_id`, and stable save-request identity; output is an immutable `incomplete` or `complete` Event Revision with completion metadata.
- Every changed save appends exactly one immutable revision and advances the Event's current-revision pointer; F-107 does not add a separate submission transition. Later edits append another revision and never rewrite one used by a plan.
- Reopening against a newer registry requires an approved migration: compatible answers are mapped with provenance, removed/incompatible answers stay visible for review, and saving remains blocked until the candidate validates under the current registry's partial-save rules.
- Conditional answers made irrelevant by a trigger change are removed or retained only as non-evaluated history according to the approved revision contract, never silently saved as active answers.
- Missing or unresolved material data stays visibly unset, unknown, pending, or failed as appropriate; it never becomes a successful or complete result.
- Invalid input produces a field or action-specific error without partial mutation. Retriable external failures preserve the user's confirmed state and expose a safe retry.

## UI and Accessibility

- The intake shows saved/saving/failed state, last successful revision, incomplete required questions, and whether the latest saved revision is eligible for normal plan generation.
- The complete workflow is keyboard operable, uses programmatic labels and visible focus, does not encode status by color alone, and announces asynchronous success or failure.
- Empty, loading, permission-denied, validation, provider-failure, and unavailable states have explicit copy and a safe next action.

## Acceptance Criteria

1. **F107-AC-01:** While its pinned registry/version is current, reopening after a successful save restores the latest revision's partial answers and registry-derived question state byte-for-byte.
2. **F107-AC-02:** A failed save is visibly unsaved and cannot append a revision or advance the Event's current-revision pointer.
3. **F107-AC-03:** An `incomplete` revision cannot create or refresh a permit plan; a `complete` revision is eligible only for normal F-201 generation, and unanswered material values remain unknown or absent.
4. **F107-AC-04:** A changed save atomically validates `base_revision_id` against the current pointer, appends one immutable `incomplete` or `complete` revision, and advances that pointer. Later changed saves append new revisions and make plan output tied to an older revision stale; no save rewrites a revision or uses a separate submission state.
5. **F107-AC-05:** Two stale clients cannot silently overwrite each other; the later conflicting save is rejected with a reload/reconcile path.
6. **F107-AC-06:** When the intake registry changes, reopening uses only the approved migration path, shows removed or incompatible answers for review, and cannot save obsolete inputs or a candidate that fails the current registry's partial-save validation.
7. **F107-AC-07:** A save binds its stable request identity to the original immutable revision and pointer/staleness result, committed with that revision under a uniqueness constraint scoped to the Event the revision belongs to. One concurrent save from a shared base wins, stale saves are rejected, and a lost-response retry returns the original result without appending duplicate work. A request presenting an already committed identity is resolved from that record before the `base_revision_id` comparison under F107-AC-04, so a retry after a lost response returns the revision and pointer state that save produced rather than being rejected as stale against a pointer its own commit advanced. A deliberate later save sends a new identity and is compared normally.

   That identity is committed together with the operands that determine the revision it records: the Event, the `base_revision_id` the save was composed against, the pinned intake registry and version under F107-AC-06, and the submitted answers. A later request presenting the same identity with any different operand is refused as a conflict, appending no revision, advancing no pointer, and returning no stored result, rather than being answered with the revision the original save produced. The identity is still the key and the operands are only a precondition on reusing it, so this is not content uniqueness: two genuinely distinct saves whose answers are identical are both appended, and a repeated identity is never rejected as a duplicate value.

   The scope, the ordering, and the operand binding are stated because none is inferable and each changes what a retry does. Without a stated scope an implementation may key the identity globally or per actor, and the same client-generated value reused across two Events would then answer the second save with the first Event's revision. Without the ordering, the comparison runs first on a retry that presents the `base_revision_id` the client read, which its own committed save has already superseded, so the organizer is told their save conflicted when it succeeded and re-saving appends a second revision for one intended edit. Without the operand binding, an Event-scoped identity is answered from the committed record no matter what the request carries, so a client that reuses one value for a later save in the same Event is returned the earlier revision as though the later answers saved, and the organizer's edit is silently lost with a success response. Other specs on this branch take this rule by reference to `F411-AC-08`, which states it once for them. F-107 restates it locally instead: F-411 is a Phase 3 spec and F-107 is the Phase 2 intake save the rest of the branch reads revisions from, so declaring a Phase 3 blocker here would gate the earlier phase on the later one. If the rule is later promoted to an approved shared invariant, this spec cites that invariant and the restatement is removed.

8. **F107-AC-08 (legacy projection, from the approved contract):** While any Phase 1 reader still uses the `events` projections, a save succeeds only when its revision projects losslessly and satisfies every legacy column constraint. A save omitting a legacy-required value is **rejected without appending a revision or changing any projection**; the server never retains the previous value, substitutes a default, or writes `NULL` to make the save appear compatible. A true no-op changes neither the projections nor `revision_counter`, while every changed save updates both in one transaction. Incomplete saves that cannot meet this rule activate only after the last legacy reader has atomically cut over.

   This bounds F-107's core feature rather than decorating it, so it is stated rather than assumed. `events` is that Phase 1 reader today: no `event_revisions` table exists, and migration 001 puts `NOT NULL` on thirteen columns the save has to fill. Twelve are questionnaire projections the revision supplies — `borough`, `location_type`, `headcount`, `event_date`, `event_open_to_public`, `food_present`, `selling_anything`, `amplified_sound`, `structure_types`, `open_flame_or_cooking`, `generator_present` and `alcohol`. The thirteenth, `name`, is not one of them: `docs/EVENT-REVISION-CONTRACT.md` §2.2 makes `answers_json` authoritative for questionnaire answers only and defines the organizer-facing name as stable Event metadata whose update appends no revision, and the intake registry has no `name` field for a revision to answer. `events.name` is therefore satisfied from that metadata authority, under the Event concurrency token §2.2 requires, and a revision is never asked for it; requiring one would either reject a valid partial revision for an already-named Event or duplicate stable metadata into `answers_json`, both of which that contract forbids. Incompleteness and legacy compatibility are two separate tests, and an incomplete revision can pass both: a street event that has answered all twelve of those questionnaire columns but not yet `street_event_size` is incomplete under the current registry, which asks that question when `sapo_event_type = street_event`, while migration 001 leaves that column nullable, so the revision projects losslessly and saves. What AC-08 rejects is the narrower case where an unanswered question is one of the `NOT NULL` columns. Until cutover, therefore, the saveable subset is narrower than "any incomplete intake," and a build that widens it by writing defaults or nulls violates `docs/EVENT-REVISION-CONTRACT.md` rather than extending this spec. The criterion asserts no new rule; it restates that contract (recorded as the ratification of SPEC-CONFLICT #213, 2026-08-02).

9. **F107-AC-09 (delivery fence on the pointer advance, from the approved contract):** Advancing `events.current_revision_id` and a worker's irreversible provider handoff of a plan-derived message job are linearizable through one shared eligibility fence. A worker that leased such a job before the save, paused after its final cancellation, current-plan and current-revision checks, and resumed at the handoff cannot deliver after the save commits: either the save wins the fence and the job cannot cross the handoff, or delivery wins it and the save observes that ordering rather than committing first. A recheck followed by an unfenced provider call does not satisfy this criterion.

   Marking the old plan stale is a label, and a label stops no send. `docs/EVENT-REVISION-CONTRACT.md` §2.5 makes a plan-derived job delivery-eligible only while its immutable source plan is `events.current_plan_id` and that plan's `event_revision_id` is `events.current_revision_id`, so advancing the pointer is meant to suppress delivery from the stale accepted plan before any replacement plan exists. The same section then says what makes that suppression real: cancelling a pending job is insufficient once a worker has leased it, and every Event operation that can obsolete a plan-derived job, a revision save included, must share the fence whose authority runs from the worker's final eligibility checks until the provider has accepted delivery or the handoff can still be cancelled. Without that requirement here, an implementation satisfying AC-04 alone advances the pointer, labels the plan stale, and lets the leased job hand the organizer obsolete regulatory guidance after their correction committed: a filing deadline computed from answers they have since changed. §4 of the contract already requires the proof: a worker that leased a plan-derived job before a changed revision save cannot send it after the save advances `current_revision_id`, including when it pauses after its final eligibility check and resumes at the provider handoff.

   **What this criterion needs that is not approved today.** F-107 owns only the revision-save side of the fence: it may not commit a pointer advance outside the fence, and it may not substitute an F-107-private lock. The fence itself is shared. `docs/EVENT-REVISION-CONTRACT.md` §3 assigns `current_plan_id`, acceptance and workflow reconciliation to the approved plan-acceptance contract, and forbids a feature bundling another row's work merely because the contract names the shared boundary, so the fence's representation, its lease-to-handoff protocol with the deliverer, and the acceptance-side participant are not F-107's to define. This criterion is therefore truthful and testable as an obligation on the save, and implementable end to end only once the plan-acceptance contract and the reviewed message-job and OpenAPI contracts named in System Impact exist. Those are added to the approval blockers below rather than assumed.

10. **F107-AC-10 (deterministic legacy backfill and the writer-authority boundary, from the approved contract):** F-107's forward migration performs the deterministic historical backfill and proves the writer-authority boundary, or it aborts. `docs/EVENT-REVISION-CONTRACT.md` §3 assigns the `jurisdiction_code` backfill, Event Revisions, the revision pointer and the plan foreign key to F-107, and §2.6 states the behavior; AC-08 governs saves after the revision path exists and reaches none of this. The migration:

    - aborts before mutating any row on no match, multiple matches, an unhandled column, or a missing or ambiguous transform in the approved compatibility package;
    - resolves and validates each plan snapshot under its mapped Event Input schema before comparing snapshots, and canonicalizes only through that schema's lossless transform;
    - creates one `complete` legacy revision per distinct `(event_id, event_revision, input_schema_version, canonical answer set)` and binds every matching plan to it, so plans generated either side of a schema change keep separate exact inputs even when the legacy counter did not move;
    - builds the current Event and current revision from the Phase 1 row under the package's exact cutover `input_schema_version` and `jurisdiction_code`, which for this ratified single-jurisdiction contract is `US-NY-NYC`, including for an Event with no historical plan, and never copies current-only values backward into plan-backed revisions;
    - orders backfilled revisions deterministically: the original numeric `permit_plans.event_revision` ascending, F-107's own tie-breaker only among distinct snapshots sharing one counter and never inferred from version-string sorting or migration execution time, every plan-snapshot revision below the current-row revision, and every later live append above all of them;
    - gives every migration-created revision `created_by`, `created_at` and `supersedes_revision_id` of `NULL`, which stays reserved for this path;
    - populates each preserved plan's provenance only from the package's approved recovery entries, writing the explicit `not_applicable` state where evidence proves no compatibility transform was used and the `legacy_unrecorded` null sentinel only where a value is unrecoverable, while new plan writes reject that sentinel; and
    - sets `events.current_revision_id`, preserves every existing plan and synthetic history, and aborts the transaction rather than partially mutating on any failure.

    **The writer-authority boundary is part of the same criterion.** The cutover leaves no window in which a Phase 1 writer can commit an Event edit that is absent from the resulting current revision. F-107 enforces that by quiescing or locking the legacy writers, or by deploying a transactional dual-write path before the snapshot; a legacy write committed before the snapshot is included in that revision, and after cutover every write goes through the revision transaction. If F-107 cannot prove the boundary, the migration aborts. Without this, an activation limited to AC-01 through AC-09 can snapshot rows while a legacy edit commits beside it and leave a just-saved answer absent from `current_revision_id`, or bind a historical plan to a revision whose answers it never evaluated. Neither is visible afterwards: the organizer sees a current questionnaire missing a correction they made, and a plan whose recorded inputs are not the ones it ran on.

    **What §2.7 does and does not add here.** §2.7 owns deterministic finding and plan-outcome comparison, and §3 assigns the diff to its first approved consumer, F-103 or F-503, not to F-107. What it binds in this criterion is the sentinel semantics the backfill writes: `legacy_unrecorded` compares equal only to itself and differs from every concrete value, `not_applicable` differs from both `legacy_unrecorded` and every concrete transform version and checksum, and a plan carrying any unrecorded provenance field can never be represented as exactly replayable. A backfill that collapses those three states into one satisfies §2.6's letter and destroys the distinction §2.7 depends on, which is why the recovery rule above is written in those exact states.

11. **F107-AC-11:** Every operation this feature defines names the Event it acts in and the workspace that owns it, and is admitted only by the acting actor's current F-702 membership of that workspace together with the F-703 permission approved for the action, both re-read server-side from stored membership and role at the moment of the operation and, for a write, inside the same transaction that commits it. That covers the changed save that appends a revision and advances the current-revision pointer under F107-AC-04, F107-AC-07, F107-AC-08, and F107-AC-09, the reopen and restore read of the latest revision under F107-AC-01, the registry-migration reopen and the candidate save it validates under F107-AC-06, and every completion and plan-eligibility read the UI and Accessibility section shows. F107-AC-10's backfill migration is an operator-run migration path and not a user operation, so it is outside this criterion. A request failing the check is refused before any durable write and before any answer value, completion state, or revision is disclosed, and its response does not distinguish an Event that does not exist from one the actor may not see. The check is at the operation and not at session start or workspace switch, so authority removed while a request is in flight causes that request to fail rather than commit.

    Without this criterion F107-AC-01 through F107-AC-09 all pass for a caller who names another workspace's Event. They fix restoration fidelity, failed-save visibility, plan eligibility, atomic append and pointer advance, conflict rejection, registry migration, request identity, the legacy projection, and the delivery fence, and not one asks who the actor is; workspace scoping appears only in the System Impact privacy row, which is not an acceptance criterion an implementation is built to. The surface that set leaves open reads another organizer's partial answers, which that same row says may contain sensitive event details, and appends revisions to their Event that advance its pointer, make their plans stale, and suppress their pending plan-derived deliveries under F107-AC-09.

    One input this criterion needs is not established by any approved artifact today and is not invented here. F-703 is PROPOSED and names no role set, so the permission above cannot be named. Until F-703 is approved this criterion is testable only as "every revision save, reopen and restore read, registry-migration reopen and candidate save, and completion or eligibility read is refused unless the acting actor holds an active membership of the workspace that owns the named Event, read server-side at that operation, and a refusal discloses nothing about whether that Event exists", not against a named role or permission identifier. Naming the revision save and read permissions with F-703 is an approval blocker below.

## Fixtures and Verification

- Planned automated fixture IDs are the acceptance IDs above; each must map one-to-one to a runnable test before approval can claim implementation readiness.
- Regulatory fixtures: F-101 approved input scenarios A–F are reused to verify partial-to-complete saves; expected regulatory outputs remain owned by F-201/F-102.
- F107-AC-07 includes a fixture in which a save commits, its response is lost, and the retry presenting the same request identity and the pre-save `base_revision_id` returns the original revision and pointer result rather than a stale-base rejection, appending no second revision, and a mismatched-reuse fixture in which that committed identity is re-presented in the same Event with different submitted answers and is refused as a conflict, appending no revision, advancing no pointer, and returning neither the stored revision nor the later answers.
- F107-AC-11 includes a fixture in which an actor holding no membership of the owning workspace names a valid Event and is refused at the save, the reopen and restore read, the registry-migration reopen and candidate save, and the completion and eligibility reads, with a response that does not distinguish absence from denial, and a fixture in which membership removed while a save is in flight fails the request rather than appending the revision or advancing the pointer.
- Security-sensitive and cross-workspace paths require negative authorization tests; provider paths require success, duplicate-delivery, retry, invalid-signature, and permanent-failure tests where applicable.
