# F-601 · Free-Text Event Intake

**Status:** PROPOSED (2026-07-26) — ready for review; not implementable until approved and listed in `docs/BASELINE.md`.

**Phase:** 4 · **Issue:** [#57](https://github.com/jzeng151/pop-engine/issues/57) · **Owner:** TBD · **Reviewer:** product owner plus affected architecture, contract, security, and lane owners (TBD) · **Approval date:** —

## Purpose and User Outcome

An organizer can describe an event in free text and receive proposed structured F-101 answers, but only confirmed values reach F-109 scope-support classification or evaluation.

## Scope

**In scope**

- Send bounded organizer text through the approved AI gateway and map proposals only to current intake-registry fields/options.
- Show evidence snippets/confidence where available, allow accept/edit/reject per field, and run F-109 scope-support classification.
- Present a material concept with no current registry field as an unmatched-scope review item that the organizer can confirm or reject; it is never an engine answer.
- Require the organizer to confirm that the original description is fully represented or manually add an unmatched-scope item before evaluation.
- Create a normal event draft/revision only from explicit confirmations.

**Non-goals**

- Direct evaluation of free text, automatic submission, new intake fields, regulatory interpretation, or silent defaulting.
- Using AI output as a regulatory source.

## Dependencies and Baseline

- F-101, F-109, F-304 AI gateway, Event Revisions, and the F-701/F-702/F-703 gate. F-702 supplies the workspace membership boundary the AI run, its proposals, and the Event resolve against and F-703 supplies the permission matrix `F601-AC-08` checks; F-701 supplies the authenticated actor both read from. All three are PROPOSED, so the gate is not an approved input today and this spec is not implementable against it until they are approved and listed in `docs/BASELINE.md`.
- Approved prompt/model, extraction evaluation set, privacy, retention, and field-confirmation contract.
- Baseline at draft time: PRD, Roadmap, Design, and Phase 0–1.5 Architecture approved 2026-07-22; `ARCHITECTURE-FUTURE.md` approved as a planning target 2026-07-25; NYC ruleset `nyc.v2.7`, rules schema `popengine-rules/v2`, and scenario fixtures v5 where regulatory output is consumed.
- Operand binding and replay ordering for client-supplied identities: `specs/F-411-staff-roles-credentialed-entry.md` F411-AC-08 states once, for this whole branch, that a client-supplied identity is committed with the operands that determine its recorded result and that a reuse carrying different operands is a conflict rather than a replay, and that a committed identity is resolved before any version, generation, state, or limit check whose answer the committed operation itself changed, while the acting actor's current authority is re-read at the replay and must still admit the operation before any stored outcome is returned. Every identity criterion below relies on it. F-411 is PROPOSED, so that rule is not an approved input today and this spec is not implementable against it until F-411 is approved or the rule is promoted to an approved shared invariant; F411-AC-08 records both paths.
- The approval PR must re-pin any baseline version that changes before approval. A proposed or superseded input blocks implementation.

## Inputs, Outputs, State, Validation, and Errors

- Input is bounded free text, registry/version, a stable run-request identity, and, on every review action, the exact proposal version and run review generation it was composed against plus, on a manual unmatched-scope addition, its own request identity, all under F601-AC-07; output is field-level proposals with provenance and no committed answers.
- Each proposal is pending → accepted/edited/rejected; only accepted/edited values enter the draft.
- Unsupported concepts, ambiguity, missing material facts, model failure, and unsafe content remain visible through F-109 or manual intake. A confirmed unmatched-scope item is a scope-support input outside the engine answer registry.
- Missing or unresolved material data stays visibly unset, unknown, pending, or failed as appropriate; it never becomes a successful or complete result.
- Invalid input produces a field or action-specific error without partial mutation. Retriable external failures preserve the user's confirmed state and expose a safe retry.

## UI and Accessibility

- Review lists original text and every proposed field/value/reason, supports keyboard bulk navigation but requires explicit material confirmation.
- The complete workflow is keyboard operable, uses programmatic labels and visible focus, does not encode status by color alone, and announces asynchronous success or failure.
- Empty, loading, permission-denied, validation, provider-failure, and unavailable states have explicit copy and a safe next action.

## Acceptance Criteria

1. **F601-AC-01:** The model can propose only fields/options present in the exact current intake registry and cannot create an endpoint, enum, or rule.
2. **F601-AC-02:** No proposed field value or unmatched-scope observation reaches scope-support classification or evaluation until the user accepts, edits, or confirms it.
3. **F601-AC-03:** Evaluation remains blocked until the organizer confirms the original description is fully represented and can manually add any model-omitted unmatched-scope item; every material concept with no current registry field must then be rejected as inapplicable or confirmed as unmatched scope. Confirmed unmatched scope enters F-109, never the engine answer set, and cannot yield a complete-plan claim.
4. **F601-AC-04:** Rejecting a proposal leaves the corresponding answer absent; editing uses normal F-101 validation.
5. **F601-AC-05:** Provider/model/prompt failure preserves the original text and offers the complete manual F-101 path.
6. **F601-AC-06:** The start-run request carries a client-generated request identity, and the transaction that creates the run commits that identity under a uniqueness constraint on `(workspace, actor, request identity)` in the AI-run table this feature owns. A retry presenting the same identity returns the original run and its proposals instead of starting a second one, so a run that commits with a lost response cannot consume provider quota twice or leave two independently actionable proposal sets. Deliberate regeneration from the same or edited text sends a new identity and is therefore never mistaken for a retry. Uniqueness over the submitted text is not that enforcement: identical text is a legitimate second run, so it would refuse deliberate regeneration while a lost create response still produced two runs. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. The acting actor's current authority is not among the checks the identity is resolved past: the authority this feature requires for a first attempt is re-read server-side at the replay, and the stored outcome is returned only if it still admits the operation, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.

   The scope is the actor inside their workspace, not a draft, because no draft aggregate exists to scope it to. `docs/EVENT-REVISION-CONTRACT.md` has no independently mutable questionnaire draft, F107-AC-08 and F503-AC-04 both forbid one, and on the pre-event path the Event itself does not exist until confirmed proposals are saved. An earlier wording said "scoped to the draft", which left an implementer to invent that entity or to pick an unstated Event or actor scope, and the two paths would then have disagreed about what a retry even means. Workspace and actor exist on both paths under the F-701/F-702/F-703 gate this spec already depends on, and the run row belongs to the bounded AI-run migration the System Impact table already declares, so nothing new is required to enforce it. A run that targets an existing Event additionally records that Event; the recording is provenance and does not narrow the constraint, so a retry is recognized identically before and after an Event exists.

7. **F601-AC-07:** Every review action names the exact version of the item it was composed against and commits only by compare-and-swap on that version. Accepting, editing, or rejecting a field proposal names that proposal's current version; a transition naming a superseded version is rejected, changes no disposition or value, and returns the current proposal for the organizer to reload and re-review, never a last-write-wins overwrite. The same rule covers every sibling reviewable item in the run and not only a field proposal: an unmatched-scope item's confirm or reject under AC-03, a manually added unmatched-scope item, and the AC-03 full-representation confirmation each name the version they were composed against and are applied on the same terms. Each of those review actions also commits its own stable client-supplied request identity, distinct from AC-06's run identity, from the final-confirmation identity below, and from every other review action's, under a uniqueness constraint scoped to the item it dispositions, in the same transaction as the disposition it records; a request presenting an already committed identity is resolved from that record before the version comparison above and returns the disposition that request originally recorded, changing no value and advancing no review generation a second time. Without it, an accept, edit, or reject that commits with a lost response is retried against the item version the commit has already advanced and is rejected as stale, so the organizer is told to reload and re-review a decision that in fact took effect, and re-deciding advances the run's review generation a second time for one intended action. Final confirmation additionally names the run's complete review generation, which advances on every one of those transitions, and compare-and-swaps that exact generation inside the transaction that builds the revision; a generation that has moved rejects the confirmation, appends no revision, and requires the organizer to re-review the current proposal set.

   Final confirmation also carries its own stable client-supplied request identity, distinct from AC-06's and from the manual-addition identity below, committed atomically with the Event and revision it writes: on the pre-event path under a uniqueness constraint scoped to the actor and workspace, since no Event exists yet to scope it to, and on the existing-Event path scoped to that Event. It is resolved before the review-generation and base-revision comparisons, so a retry after a lost response returns the Event and revision the first attempt committed rather than being answered as a stale conflict for work that in fact succeeded. Nothing else identifies this write: AC-06's identity names creation of the AI run and is consumed by the run that already exists, and this criterion's generation and base-revision comparisons name the state the confirmation was composed against rather than the request that made it. Without it, a lost response on the pre-event path lets the retry create a second Event and first revision for one confirmation, and on an existing Event the first save advances the revision the retry named, so the organizer is told their confirmation was stale when it had already committed. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch, so a reuse naming a different run, review generation, or base revision is refused as a conflict rather than answered with the committed Event.

   A manual unmatched-scope addition creates the item it acts on, so it has no prior version for the request to name and compare-and-swap cannot make its retry safe on its own. That creation therefore binds a stable client-supplied request identity, committed with the item under a uniqueness constraint scoped to the run, in the same transaction that appends the item and advances the run's review generation. A retry presenting the same identity returns the original item and the generation that creation reached, appends no second review item, and advances the generation no further; a deliberate second manual addition, including one carrying the same text as an existing item, sends a new identity and is created as its own item. Once created, the item's later confirm, reject, edit, and removal are ordinary review actions governed by the version comparison above. AC-06's identity does not reach this: it is scoped to run creation on `(workspace, actor, request identity)` and is consumed by the run that already exists. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. The acting actor's current authority is not among the checks the identity is resolved past: the authority this feature requires for a first attempt is re-read server-side at the replay, and the stored outcome is returned only if it still admits the operation, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.

   Comparing only the run's review generation is not that protection either, in either direction. A retry that names the generation it read before the first attempt finds that the committed first attempt has already advanced it, so the retry is rejected as stale and the organizer is told their addition failed when it succeeded; a retry that names the generation the first attempt reached passes the comparison and appends a second review item for one intended addition, which AC-03 then requires the organizer to confirm or reject twice and which enters F-109 twice. The identity and the generation are both required and do different work: the identity decides whether this request has already been applied, and the generation decides whether the review set it was composed against has moved.

   AC-02 keeps an unconfirmed value out of scope-support classification and evaluation and says nothing about which confirmed set the revision is built from. Without these comparisons two tabs accepting, editing, or rejecting one proposal both report success and the later write silently replaces the disposition the organizer was told had saved, and a final confirmation racing one of those actions builds the revision from a disposition or unmatched-scope set other than the one shown at review. AC-02 sees a confirmed value in each case, so what reaches F-109 or evaluation is a value the organizer never confirmed.

8. **F601-AC-08:** Every operation this feature defines names the AI run, proposal, or Event it acts on and the workspace that owns it, and is admitted only by the acting actor's current F-702 membership of that workspace together with the F-703 permission approved for the action, both re-read server-side from stored membership and role at the moment of the operation and, for a write, inside the same transaction that commits it. That covers starting an AI run under `F601-AC-06`, where a refused start commits no run row and issues no call through the F-304 gateway to the provider behind it; accepting, editing, or rejecting a field proposal, confirming or rejecting an unmatched-scope item, a manual unmatched-scope addition, and the full-representation confirmation under `F601-AC-07`; the final confirmation that creates an Event and its first revision or appends a revision to an existing Event under `F601-AC-07`, checked inside the transaction that commits it; and every read of a run, its status, and its proposals. `F601-AC-06`'s uniqueness constraint on `(workspace, actor, request identity)` is not a partial form of this check: it is a retry-recognition key that decides whether a run already exists, it is idempotency and not authorization, and it admits nothing. A request failing the check is refused before any durable write, before any original text, proposal, snippet, or disposition is disclosed to the caller, and before any of the organizer's text is sent to the external AI provider, so a refused operation discloses nothing to either party. The response does not distinguish a run, proposal, or Event that does not exist from one the actor may not see. The check is at the operation and not at session start or workspace switch, so authority removed while a request is in flight causes that request to fail rather than commit.

   Without this criterion AC-01 through AC-07 all pass for a caller who names another workspace's run or Event. They fix what the model may propose, what reaches classification and evaluation, how rejection and editing behave, how failure degrades, and which exact versions and identities each action commits against, and not one of them asks who the actor is. The surface that set leaves open reads another organizer's original free text and its proposals, dispositions their review items, and, through final confirmation, creates or extends an Event in their workspace; starting a run additionally forwards the named text to the external provider, so an unauthorized start is a disclosure to a third party and not only a write.

   One input this criterion needs is not established by any approved artifact today and is not invented here. F-703 is PROPOSED and names no role set, so the permission above cannot be named. Until F-703 is approved this criterion is testable only as "every run start, review action, confirmation, and read is refused unless the acting actor holds an active membership of the workspace that owns the named run, proposal, or Event, read server-side at that operation, and a refusal discloses nothing about whether that aggregate exists and sends nothing to the provider", not against a named role or permission identifier. Naming the intake-run and review permissions with F-703 is an approval blocker below.

9. **F601-AC-09:** The AI run, every proposal and unmatched-scope item being confirmed, the base revision a confirmation names, and the Event the confirmation targets or creates must all resolve to the same workspace, compared server-side inside the transaction that commits the confirmation and at every review action that dispositions an item. Where the run names an Event, the comparison is made at that scope as well and not instead: a run started against an existing Event may be confirmed only into that Event, and its base revision must be a revision of that Event. F601-AC-06 scopes the run-creation identity to `(workspace, actor, request identity)`, which records where the run was created and admits nothing; F601-AC-07 compare-and-swaps the item versions, the run's review generation, and the base revision, which proves each is current wherever it lives; F601-AC-08 admits the operation by the acting actor's current membership of the workspace that owns whichever aggregate the request names. An actor holding an active membership of workspace A and an active membership of workspace B satisfies all three while confirming a run and proposal set from A into an Event in B, or into a new Event created in B: every version is current, every generation matches, and the actor is legitimately authorized on both sides. The Event comparison closes the same gap one membership wide: F601-AC-06's identity is scoped to the workspace and records nothing about an Event, so a run started for event A and a confirmation naming event B's current base revision satisfy the workspace comparison and every version comparison alike, and no criterion above would let an implementer refuse it.

   What commits is the organizer's original free text and the accepted proposals from the source, written into the target Event's history as an ordinary F-101 revision. The target's members then read the source description through the revision, and everything downstream treats it as the target's own input: F601-AC-02 releases the confirmed values into scope-support classification and evaluation, so the source answers reach the target's verdict, plan, and checklist. Across two events of one workspace that is the likelier mistake and the harder one to see, because both events are legitimately the organizer's and the revision history gives no sign the text was composed about the other one. On the pre-event path the new Event is created carrying that text as its first revision, so there is no earlier state to compare it against, and there is no source Event to compare either, which is why the Event half applies only when the run names one. The source side shows nothing, because a run being read and confirmed elsewhere changes nothing there. F601-AC-08's own explanation covers the caller who holds no membership near the run; this is the caller who holds one on each side, or one membership spanning both events.

   This applies `F702-AC-10`'s fourth obligation, which states once for the whole feature set that every record an operation names must resolve to one workspace, to the run, proposal set, and target this confirmation names together. `F604-AC-09` states the same rule for the F-602 proposal, source document, and target record a reconciliation pairs, and `F602-AC-09` and `F603-AC-08` state it inline for the target an accepted value or a reassignment names; this is that rule applied to the confirmation that writes an Event revision, and it is stated here because an implementation is built to this spec's criteria. The Event half is the narrower-scope sentence of that same obligation, which requires the comparison to be made at a spec's own aggregate as well as at the workspace, not instead of it; `F406-AC-09` and `F407-AC-08` state the pair the same way for the versions a P&L and a post-mortem pin. On the pre-event path the Event does not exist when the confirmation begins, so the comparison is against the workspace the run resolves to and the workspace the request names for the Event it is about to create, which is the same shape `F105-AC-08` uses for a target that the operation composes rather than reads; there is no Event on either side to compare, and the Event half is satisfied vacuously rather than waived. A mismatch on either scope rejects the confirmation in full, creates no Event, appends no revision, changes no disposition, advances no review generation, sends nothing further to the provider, and returns a response that does not distinguish a run, proposal, revision, or Event that does not exist from one that resolves to a different Event or workspace. The two halves have different approval states and are stated so an implementation can build the half that is available. The Event a run and a revision resolve to is an approved input today, so the Event comparison is implementable and testable now as "a review action or final confirmation whose run names one Event and whose target Event or base revision names another is refused, writes no Event and no revision, and discloses neither side". F-702 is `PROPOSED`, so the workspace a record resolves to is not an approved input today and that half is not implementable until F-702 is approved and listed in `docs/BASELINE.md`.

## Fixtures and Verification

- F601-AC-07 includes a confirmation-retry fixture on each path: on the pre-event path a lost response followed by a retry of the same confirmation identity yields exactly one Event and one first revision, and on an existing Event the retry returns the revision the first attempt committed instead of a stale-generation rejection.
- Planned automated fixture IDs are the acceptance IDs above; each must map one-to-one to a runnable test before approval can claim implementation readiness.
- Regulatory fixtures: A reviewed paraphrase corpus for scenarios A–F plus ambiguous/unsupported/adversarial descriptions; engine expectations remain the approved structured fixtures.
- F601-AC-07 includes a fixture in which a proposal acceptance commits, its response is lost, and the retry presenting the same request identity and the pre-acceptance proposal version returns the original recorded disposition rather than a stale rejection, advancing the run's review generation only once.
- F601-AC-08 includes a fixture in which an actor holding no membership of the owning workspace names a valid run, proposal, and Event and is refused at run start, at every review action and confirmation, and at every run, status, and proposal read, with a response that does not distinguish absence from denial and with no request reaching the F-304 gateway or the provider, and a fixture in which authority removed while a run start or final confirmation is in flight fails that request rather than committing.
- F601-AC-09 includes a fixture in which an actor holding an active membership of two workspaces confirms a run from one against an existing Event in the other and is refused with no revision appended and a response that does not distinguish absence from a different workspace, an equivalent fixture on the pre-event path proving no Event is created, a fixture in which a single review action dispositions a proposal belonging to a run in another workspace and is refused, a sibling-event fixture in which a run started for event A is confirmed against event B of the same workspace while naming B's genuinely current base revision and is refused with no revision appended and no disposition changed, and a same-Event control fixture in which the identical confirmation commits.
- Security-sensitive and cross-workspace paths require negative authorization tests; provider paths require success, duplicate-delivery, retry, invalid-signature, and permanent-failure tests where applicable.
