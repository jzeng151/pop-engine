## User Story

As an independent organizer, I turn my permit plan into a living checklist where I track each application's status and keep its documents, so execution has one home instead of seven agency portals.

## Inputs

- Latest `permit_plans` + `permit_plan_items` for the event.
- User actions: status changes, notes, file uploads.
- On a conversion or review, the id of the plan the organizer was being shown. Required, not
  optional: Acceptance Criterion 10 turns on the server being able to tell which plan was read, and
  a caller that does not say cannot have that checked.

## Outputs

- `POST /api/events/:id/checklist` → `checklist_items` rows (one per permit/insurance plan item; advisories render as read-only context, not trackable tasks). Creation also schedules F-203 alerts.
  - Takes a JSON body naming the plan being displayed (`planId`). Absent or malformed, the request is refused (400) rather than defaulted to the latest plan, because defaulting is the behaviour Acceptance Criterion 10 exists to remove.
  - Where that plan is no longer the latest, the request is refused (409) and the response carries the newer plan's checklist so the organizer can be re-presented with it. Nothing is materialised and no review is recorded (Acceptance Criterion 10).
  - The pre-existing refusal when the EVENT has moved past the plan is unchanged and is also a 409; the two are distinguished by the stale-plan case naming the superseded plan id.
- `PATCH /api/checklist-items/:id` → status/notes update.
- `POST /api/checklist-items/:id/documents` → upload streamed to S3-compatible storage; metadata row in `documents`.
- `GET /api/documents/:id/url` → short-lived signed download URL.

## Acceptance Criteria

1. One click converts the latest plan into a checklist; each item stays linked to its plan item (and thus rule, deadline, citation, portal).
2. Statuses: not_started → in_progress → submitted → approved / rejected; any transition is allowed (agencies are messy), current status is always visible per item, and the event rollup counts current-plan items only. Retained items from an earlier plan are counted and labeled separately so the rollup never appears to omit visible rows.
3. Document upload accepts PDF/PNG/JPG up to 10 MB; the file lands in object storage; download works via signed URL; nothing binary in Postgres.
4. Notes persist per item.
5. Checklist shows each item's `latest_apply_date` (and `apply_after_date` when gated) so the deadline context lives where the work happens.
6. Regenerating the plan (rescope) prompts: existing checklist is kept but flagged "plan has changed; review items" with items no longer in the new plan struck through, new items appended. Nothing is silently deleted.
7. Demo path: Scenario A rescope → plan passes → checklist created → one status flipped and one document uploaded live.
8. The checklist response exposes each item's source plan `ruleset_version` and `snapshot_date` through its existing plan-item relationship. The values are never copied from the live rules file or duplicated into checklist storage.

   **Which plan a row is attributable to is decided by whether the row is STRUCK THROUGH**, and not by why it was struck or by whether the latest plan raises the requirement again. A row that is not struck through is attributable to the latest plan, whose recalculated values it displays. A row that is struck through is attributable to the plan its persisted item belongs to, which is the last plan that raised it AS THIS ROW'S TASK. Both branches read the values and the provenance off one object, so neither can print a pair that never existed, which is the guarantee this criterion has always been for.

   The wording this replaces, "a retained row stays attributable to the last plan that raised it", was true of every case that existed when it was written and became ambiguous when Acceptance Criterion 9 made a dropped task terminal. For a terminally struck row the latest plan does raise the requirement, on the same rule-id set and the same kind, but it did not raise THIS row's task, and "the last plan that raised it" no longer picks one of those out. It now says which.

   **Keyed on the state rather than on the circumstance, which is the third time on this criterion that the same correction has been the answer**: the kind rule was keyed on whether the replacement was trackable when it should have been keyed on kind identity, the provenance floor was keyed on a previous date being named when it should have been keyed on a previous state being rendered, and this was keyed on why a row was struck when it should have been keyed on the fact that it is struck. Each time the fix collapsed a case rather than adding one, and this is no exception: struck and not-struck give the same two answers as before for every row that existed before Acceptance Criterion 9, so nothing is added, and the terminal row stops falling between them. A reader who sees the shape should apply it to the fourth instance before it becomes a finding.

   F-206 Acceptance Criterion 4 selects the same rows on the same key, having been re-keyed to whether a row is struck through, so a terminally struck row takes its struck-through case and is attributed to the plan its persisted item belongs to, which is what this criterion requires. The two were reached independently rather than either deferring to the other, and each now carries the key in its own words. Where they once parted was the key and never the outcome: F-206's earlier binary sorted a terminally struck row into still-required because it asked whether the latest plan still raises the requirement, which is the key both criteria have moved off. Its reading of this criterion, that "the last plan that raised it" means the latest plan for a requirement that survives, stays true for every row it was written about, and the terminal row it did not reach is reached now by its own struck-through case.

   The implementation does not match: attribution is currently chosen by whether the latest plan holds an item for the same rule-id set, which for a terminally struck row selects the latest plan. Bringing the code to this criterion is not a spec change and is not made here.

9. **Moved computed deadline.** This criterion applies to a row the latest plan still raises, and only to one. A **dropped** row — kept and struck through by Acceptance Criterion 6 because the latest plan no longer raises the requirement — has no item in the latest plan, so there is no current date and no current deadline state for it to be compared against: the comparison below has one operand, not two. Such a row never carries a moved-deadline notice. It is not silent about anything as a result: the strike-through already says the requirement is no longer raised, and its dates remain the last plan's that did raise it, attributed to that plan, which is F-206 Acceptance Criterion 4's rule and not this one's to restate. Stated here because an implementation reading only the comparison would find no matching item and have to invent an answer.

   **A requirement is its rule-id set AND its kind, and a kind change ends the task.** "Still raises" above means the latest plan carries an item for the same rule-id set AND of the same kind. Where the kind differs, the requirement the organizer was tracking is not the one the latest plan raises: the task is kept and struck through exactly as one the latest plan no longer raises, keeps the status, notes, documents, values and attribution it had, is not re-pointed by a review, and carries no moved-deadline notice, which is the one-operand case the paragraph above already describes.

   **A struck-through task is terminal, so a kind that comes back is a new task and never a revived one.** Dropping is one-way. "Still raises" applies only to a row that has not been struck through, so a row struck through by a kind change is never re-pointed however many later plans raise that rule-id set and kind again. Without this the definition contradicts itself on the third plan of `permit` to `insurance` to `permit`: the struck permit row matches the returning item on rule-id set and kind, while the insurance row's own kind change makes the same returning item a new task, and both cannot have it. The persisted shape agrees rather than merely coping: `checklist_items.plan_item_id` is UNIQUE, so two rows pointing at one latest item is not a state the database can hold.

   **Reactivating was the alternative and it is refused for the reason the rest of this criterion is written.** Re-pointing the struck row would assert that work done against the earlier requirement satisfies the returned one, and nothing the row compares establishes that. A published plan in between said the requirement did not apply in that form; whether an approval survives that gap is a question about the organizer's filing and their agency's procedure, which is exactly the claim Acceptance Criterion 9 refuses to make about a moved date and rejected in resolving SPEC-CONFLICT #121. The organizer loses no record either way, because the struck row keeps its status, notes and documents attributed to the plan that raised it; what it does not do is carry them onto a task it cannot vouch for.

   Identity therefore needs no third component. A requirement is still its rule-id set and its kind; what this adds is that a ROW has a lifecycle, and that the lifecycle ends once. That is Acceptance Criterion 6 read literally, since it strikes through and appends and provides no way to un-strike anything.

   Where the replacement goes needs no rule of its own, because the Outputs contract already decides it. A replacement that is a permit or insurance item is a new item and is appended as a new task, unstarted. A replacement of any other kind is rendered where every non-trackable finding is rendered, as current read-only context. Both are Acceptance Criterion 6 applied unchanged: struck through what the latest plan no longer raises, new items appended, nothing silently deleted.

   **This is keyed to kind identity rather than to trackability, and that is a correction to how this clause was first written.** An earlier revision keyed it to whether the REPLACEMENT was still trackable, which answered the permit-to-advisory case and left permit-to-insurance untouched: both ends trackable, so the row read as surviving. But trackability was never what made the first case wrong. What makes both wrong is the same thing, that the organizer's recorded work is carried onto a requirement they did not do it against, and that has nothing to do with whether the replacement can be a task. Keying on identity states it once and covers the whole transition space; keying on trackability needed a second clause beside the first for the other half of it, which is how a one-sentence rule becomes a family of near-duplicates.

   **Both halves are live defects, established by running them rather than by reading the code.** Permit to advisory: the row reports itself as still in the latest plan, renders the ADVISORY's regulatory content inside a trackable task, and appears a second time in the context list, so one requirement occupies two mutually exclusive roles at once. Permit to insurance is quieter and worse: the same row keeps its id, its `kind` becomes `insurance`, and its status stays **approved** with the organizer's notes and uploaded document still attached, so an approved permit becomes an already-satisfied insurance obligation with no organizer action and nothing on screen saying anything changed. A review re-points it and clears the changed-plan prompt. The advisory case at least renders visibly wrong content; this one renders content that is plausible and false. In both, the row's persisted link still points at the old item while the row displays the new one. This criterion states the outcome; bringing the implementation to it is not a spec change and is not made here.

   For a row the latest plan does raise, the comparison is of two `latest_apply_date`s, and they come from two different places. The **previous** one is on the plan item the row is persisted against, reached through `checklist_items.plan_item_id`: the plan the checklist was last converted or reviewed against. The **current** one is on the latest plan's item for the same requirement, found by matching the requirement across plans the way the checklist already matches it, on its set of rule ids. "Previous" and never "earlier": the two are in a known sequence but not a known order, because a recalculated deadline can land later than the one it replaces as readily as sooner, and calling it the earlier date would state a relationship the dates do not carry — the kind of claim this criterion exists to refuse, made inside its own copy. Two lookups against two plans, named separately here because reading the persisted item twice would compare a date with itself and never report a change. Neither date is copied into checklist storage and neither is read from the live rules file. Which plan's values the row DISPLAYS is not this criterion's rule and is unchanged by it: a row that is not struck through displays the latest plan's recalculated dates, per F-206 Acceptance Criterion 4. This states the previous date; it does not reinstate it.

   Either side of the comparison can be absent, and an absent date does not mean one thing. The engine already separates the cases and the row reads its answer rather than inferring one from the null: `deadline_status` is `not_applicable` when no dated filing window applies at all — the rule publishes no deadline, or publishes `before_issuance`, which is listed with its parent permit and never dated independently — and `not_calculable` when a window does apply and no date could be produced for it, which is the state every `business_days_minimum` finding is in for as long as no holiday list is published for the pinned calendar (SPEC-CONFLICT #130), and also the state of a `research_required` lead time. Where the engine states why, it does so in `timeline_unresolved_reason` or `deadline_unknown_fields`; a `research_required` line has neither and carries "confirm with agency" instead.

   So the row compares **two** things, and the outcomes below are every combination of the two rather than a list of the situations anyone has thought of so far:

   - **The date** — the two `latest_apply_date`s. It moved when they differ, and one being absent while the other is not is a difference. Both absent is not.
   - **The deadline state** — what the row says about the deadline other than the date: the published deadline object **in full**, whether the finding is dated at all or is `not_calculable` or `not_applicable`, `timeline_unresolved_reason`, `deadline_unknown_fields`, `deadline_display`, and whether the task is gated at all. It moved when any of those differs.

     The deadline object is compared field by field rather than by `type` alone, because two plans can agree on `type` and still publish different deadlines: a lead-time or boundary correction changes `businessDays`, `calendarDays` or `boundary` underneath an unchanged `type`. That gap is widest exactly where it is least visible. Where neither plan can date the finding, both `latest_apply_date`s are null and `deadline_status` is `not_calculable` on both sides, so a same-type rule edit moves nothing else this criterion looks at and the row reads as untouched. Every `business_days_minimum` finding is in that state for as long as no holiday list is published (SPEC-CONFLICT #130), so this is the present condition of several rows, not a hypothetical. A plan item persists the parsed deadline object, so the fields compared are `type`, `qualification`, `display`, `boundary`, `calendarDays`, `businessDays`, `levels`, `unknownLevelBehavior`, `hardFloorDays` and `processingRangeDays`, and no others. They are named so an implementation compares a known set instead of deciding for itself which ones count; a ruleset that adds a field to the stored deadline adds it to this comparison.

     That list is drawn from what a plan **stores**, not from the field names a ruleset publishes. Those are two different sets, and reading the wrong one is how this list first came to name two fields that can never differ in it. `level_field` and `multi_block_field` are published inside a by-level rule's deadline, but the parser lifts them out to a **rule-level** binding rather than leaving them on the deadline, so they are absent from the object a plan persists. A criterion that compares stored snapshots cannot reach them at any cost short of changing what is stored. **A change to a by-level binding alone is therefore outside this comparison**, and where such a change moves no date, no status and no other stored field, this criterion is silent about it. That is stated rather than left to be discovered: an implementation must not be written as though comparing the binding were possible.

     `deadline_display` is compared with them and is **not** treated as mere wording. `DOB-ASSEMBLY-001` is the reason: its three-business-day processing floor, which governs whether a filing is handled at all, is carried only as prose, in its `output.deadline.qualification` and `output.deadline.display` in the published ruleset, because no deadline type in this schema expresses a business-day floor and adding one is a schema change needing its own approved spec. A rule can therefore change what it substantively requires of an organizer entirely inside those two strings. A comparison that skipped them would classify that as nothing moved.

     `apply_after_date` is compared too, and by PRESENCE rather than by value. Acceptance Criterion 5 renders it as the gated task's start date, so a row that becomes gated, or stops being gated, changes what an organizer is told to do next while every field above it stands still: `applyDependencySequencing` nulls the gate when the upstream decision is expected after the gated finding's own deadline, and the engine states the two readings itself, a date meaning wait until this date and null meaning there is no gate to wait for. Those are different instructions and the move between them is a state change. It is persisted and reachable on both sides: `apply_after_date` is a column on `permit_plan_items`, and the sequencing note that explains a gate lives in the same stored `finding_renderings` the rest of this comparison already reads.

     Its VALUE is excluded for the same reason the countdown statuses below are. The gate is computed as today plus the upstream decision window, so it moves on every regeneration run on a later day with nothing regulatory having changed, and comparing it would raise a notice for every gated row every time the clock advanced. Where the upstream processing range itself changes, that is a change to the UPSTREAM finding's deadline object, and `processingRangeDays` is in the compared set above, so it surfaces on the row it actually changed rather than on the row it propagates to. The residual is stated rather than left to be discovered: a regulatory change upstream that narrows only the gated row's own slack is reported on the upstream row and not on the gated one.

     One exclusion remains deliberate: a move among `on_track`, `deadline_approaching` and `published_deadline_missed` while the date stands is not a state change here, because each plan computes them against its own `today`, so treating them as distinct would raise a notice every time the clock advanced past a threshold — which is the countdown doing its job, and Acceptance Criterion 5 already shows it where the work happens.

   |                    | state unchanged                | state moved                     |
   | ------------------ | ------------------------------ | ------------------------------- |
   | **date unchanged** | nothing moved; no notice       | the row states the state change |
   | **date moved**     | the row states the date change | the row states both             |

   The date change is stated in whichever of these shapes it takes:

   - **A date on both sides.** The row states that the deadline PopEngine computes for it has changed, naming both as the previous one and the current one.
   - **A date before, none now, and the current `deadline_status` is `not_calculable`.** A filing window still applies and PopEngine could not date it. The row says so, names the previous date, and carries the reason the finding gives — `timeline_unresolved_reason` or `deadline_unknown_fields` where there is one, the "confirm with agency" treatment Acceptance Criterion 5 already requires where there is not. A row an organizer has been working to a date must not fall silent at the moment that date becomes "confirm with agency".
   - **A date before, none now, and the current `deadline_status` is `not_applicable`.** Nothing failed: the requirement no longer carries a filing date of its own. The row says that, names the previous date, and must not describe it as a date that could not be computed — the two states mean different things to an organizer, and the published meaning is the one that survives.
   - **No date before, a date now.** The row states that a deadline is now computed for it, and names it.

   **A previous value carries the state that qualified it.** Wherever the row renders anything about a previous deadline — a previous date, a previous state, or both — it also carries that value's own verification state and provenance: `verification_status`, `last_verified_date`, `sources`, `source_url`, its conflict text where it has one, and the `ruleset_version` and `snapshot_date` of the plan it came from. A missing `last_verified_date` renders no date and never borrows the snapshot date, which is F-206 Acceptance Criterion 5 and applies to a previous value exactly as it does to a current one. A date that was `RESEARCH_REQUIRED` or `OFFICIAL_CONFLICT` when it was computed is not a plain date, and showing it stripped of that state presents a qualified regulatory value as a settled one, which `AGENTS.md` requires to be visible end to end. This is a floor on what travels with the old value, not a licence to restate it as current: the previous state is labelled as the previous one, exactly as the previous date is.

   **That list is closed, and it is derived rather than assembled.** It has now been found short three times, each time by adding the one field the last reader noticed, which is why it is instead taken whole from F-206's own enumeration of what a plan line carries: the immutable `sources` snapshot with its citation and every URL, the primary `source_url`, the `verification_status` badge and the nullable `last_verified_date`, plus `conflict_text` from the stored rendering and the plan's own pinned pair. Checked against the schema, that is every provenance-bearing field a `permit_plan_items` row and its plan hold. Two are excluded deliberately: `verified_status` is a deprecated duplicate of the badge and F-206 says not to use it (issue #76), and `triggered_by` records which answers made the requirement apply, which is provenance of applicability rather than of verification and belongs to no part of this floor.

   **The floor is keyed to a previous value being rendered, not to it having had a date**, and that distinction is the whole of it. A requirement whose `research_required` lead time becomes `not_applicable` has no date on either side, so nothing above names one; the paragraph below still requires its previous state to be described, and that previous state was `RESEARCH_REQUIRED`. Keyed to a date, the floor would let exactly that value be shown as a settled one. Any undated previous state carries its provenance on the same terms as a dated one.

   The current side needs no clause here: a still-required row already displays the latest plan's verification status and sources under F-206 Acceptance Criterion 4. This criterion adds the previous side, which nothing else attributes.

   This adds nothing to storage and asks for nothing the plan did not already keep, which was checked against the schema rather than assumed. Plans are immutable snapshots, and the previous side of the comparison is the plan item the checklist row still points at until a review re-points it, so every field above is already persisted and already loaded: `permit_plan_items` carries `verification_status`, `sources`, `source_url` and `last_verified_date` per item; the row's own join reaches that item and the plan holding it, which supplies `ruleset_version` and `snapshot_date`; and `conflict_text` comes from that same plan's stored `finding_renderings`, which the checklist already loads for every plan a row points at rather than for the latest alone. Nothing here is read from the live rules file, which is the prohibition Acceptance Criterion 8 already states.

   The state change is stated as what applied before and what applies now. Where the date did not move it is stated **on its own**, and the row must not describe a date as having changed, because none did — the date on screen is the one that was there, which is exactly why such a row would otherwise look untouched. That covers a requirement moving between `not_applicable` and `not_calculable`, the difference between no filing window applying and one applying that nobody can date yet; an unresolved reason changing while the status stays `not_calculable`, where a lead time no source publishes is a different answer from a published window whose arithmetic is waiting on a holiday list; and a requirement that keeps its computed date while its published deadline type changes underneath it. Where the date moved as well, both are stated and neither stands in for the other.

   Where the two plans pin different `ruleset_version`s, the row may additionally state that they were generated from different published rulesets and name both versions; it must not name that as the cause of the move, because one regeneration can pick up an intake edit and a ruleset change together, and nothing the row compares separates them. The notice is a per-row detail of the state Acceptance Criterion 6 flags, and clears with it: reviewing the checklist re-points the row at the latest plan, after which there are no longer two plans to compare.

   **In every case this criterion produces a notice — a date change, a state change, or both — the notice must not say, imply, or link to anything about the organizer's filed application** — not that a filing needs amending, not that an agency should be contacted about it, not that a re-application may be required, not that any action is now expected of them, and equally not that nothing is required and the filing is unaffected. Both directions are claims, and neither is established by what the row can see.

   `latest_apply_date` is computed, and the inputs that move it are not all of one kind. A corrected published lead time, a boundary correction or a holiday calendar being published say nothing whatever about the organizer's event. A changed size or level input is the opposite: the event itself moved, and a filing already with an agency may well be affected by that. What the row cannot do is tell those causes apart. It compares two dates and two deadline states; a regeneration can pick up an intake edit and a ruleset change together, which is the same reason a differing `ruleset_version` may not be named as the cause. So the honest statement is the narrow one: **a change in the deadline PopEngine computes does not by itself establish anything about a filed application, in either direction.** Where an organizer's event has genuinely changed, what that requires of an existing filing is a question about their event and their agency's published procedure, and F-202 has no approved criterion for answering it on a checklist row — that claim was proposed, and rejected, in resolving SPEC-CONFLICT #121.

10. **A review acknowledges the plan the organizer was shown.** Converting a plan into a checklist — the first conversion under Acceptance Criterion 1, and every later review under Acceptance Criterion 6 — records that the organizer reviewed a specific plan. That record is only worth having if it is true, so the plan a conversion acts on must be the plan they were looking at when they acted, and an implementation must be able to establish which plan that was. This criterion does not mandate a mechanism; the contract that implements it is recorded in Outputs above, so a client built from this spec calls the endpoint the way the api actually expects.

    Where the plan they were shown is no longer the latest at the moment the conversion is processed, it is **refused or re-presented, never silently re-pointed at the newer plan**. Silent re-pointing is what makes the record false: the organizer sees one plan, acts once, and acknowledges another they have never read — and the acknowledgement is the thing Acceptance Criterion 6 later reads to decide the checklist has been reviewed. A refusal is not a dead end and must not read as an error in their work: what has happened is exactly Acceptance Criterion 6's condition arriving while they were looking, so they are shown the newer plan and offered the review again against it. Nothing is materialised by the refused attempt.

    This extends a protection F-202 already has, along the axis it currently lacks. A conversion is already refused when the EVENT has moved out from under the plan, because materialising it would present requirements computed from an intake the organizer has replaced. It is not refused when the PLAN has moved out from under the organizer, which is the same failure with the two halves swapped.

    It composes with the criteria around it rather than qualifying them. Acceptance Criterion 1 converts the latest plan, and in the ordinary case the plan shown and the latest plan are one plan, so nothing changes; where they differ, this criterion is what stops "the latest" being read as a licence to substitute. Acceptance Criterion 6 raises the review and this governs what a review may act on. Acceptance Criterion 8's provenance is per row and is untouched. Acceptance Criterion 9 says reviewing re-points a row at the latest plan and still does: a conversion that commits is one whose shown plan was still the latest, so the plan it re-points to and the plan it acknowledges are the same plan.

## Edge Cases

- Checklist created twice: idempotent; second call returns the existing checklist rather than duplicating.
- Upload failure (S3 unreachable): item keeps state, user sees a retryable error; no orphan metadata row.
- Plan with zero trackable permit/insurance items (synthetic edge case, not Scenario B): checklist creation is offered but produces an empty state with read-only context shown ("nothing to track; keep confirmation notes here if you like").
