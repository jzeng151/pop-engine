# F-715 · Rules Admin: Reported-Issue Queue

**Status:** PROPOSED (2026-07-26) — ready for review; not implementable until approved and listed in `docs/BASELINE.md`.

**Phase:** 4 · **Issue:** [#68](https://github.com/jzeng151/pop-engine/issues/68) · **Owner:** TBD · **Reviewer:** product owner plus affected architecture, contract, security, and lane owners (TBD) · **Approval date:** —

## Purpose and User Outcome

A user can report a possibly wrong, missing, or outdated requirement with exact plan context, and the verification team can triage it without the report becoming regulatory authority.

## Scope

**In scope**

- Capture category, user explanation, exact jurisdiction/ruleset/plan revision, finding/rule context when the category has one, bounded optional contact follow-up, and safe attachment if approved.
- Deduplicate/link related reports, triage, request research, close with reason, and route accepted work into F-711/F-710.
- Show the reporter a receipt and status that makes no correction promise.

**Non-goals**

- Changing a plan/rule/status automatically, crowdsourced voting, public issue disclosure, agency complaints, or treating reports as evidence.
- Guaranteeing response/resolution time without an approved service policy.

## Dependencies and Baseline

- The F-701/F-702/F-703 gate, F-711/F-710 review workflow, and approved retention/contact/attachment policy. F-702 supplies the workspace membership boundary the workspace and plan authorization of `F715-AC-05` resolves against and F-703 supplies the triage and admin-queue authority `F715-AC-10` checks; F-701 supplies the authenticated reporter identity `F715-AC-06` and `F715-AC-08` read and the authenticated actor both checks read from. All three are PROPOSED, so the gate is not an approved input today and this spec is not implementable against it until they are approved and listed in `docs/BASELINE.md`.
- Public/authenticated report abuse controls and triage state vocabulary.
- Baseline at draft time: PRD, Roadmap, Design, and Phase 0–1.5 Architecture approved 2026-07-22; `ARCHITECTURE-FUTURE.md` approved as a planning target 2026-07-25; NYC ruleset `nyc.v2.7`, rules schema `popengine-rules/v2`, and scenario fixtures v5 where regulatory output is consumed.
- Operand binding and replay ordering for client-supplied identities: `specs/F-411-staff-roles-credentialed-entry.md` F411-AC-08 states once, for this whole branch, that a client-supplied identity is committed with the operands that determine its recorded result and that a reuse carrying different operands is a conflict rather than a replay, and that a committed identity is resolved before any version, generation, state, or limit check whose answer the committed operation itself changed, while the acting actor's current authority is re-read at the replay and must still admit the operation before any stored outcome is returned. Every identity criterion below relies on it. F-411 is PROPOSED, so that rule is not an approved input today and this spec is not implementable against it until F-411 is approved or the rule is promoted to an approved shared invariant; F411-AC-08 records both paths.
- The approval PR must re-pin any baseline version that changes before approval. A proposed or superseded input blocks implementation.

## Inputs, Outputs, State, Validation, and Errors

- Inputs are bounded user report, a client-supplied submission identity under F715-AC-08, and system-captured immutable context; output is a non-authoritative queue item/receipt.
- State is new → triaged → needs-research, linked, resolved, dismissed, or closed under the approved vocabulary; the current triage version advances with every append-only transition.
- Missing context, duplicate, abusive content, or reporter disagreement never changes published output.
- Missing or unresolved material data stays visibly unset, unknown, pending, or failed as appropriate; it never becomes a successful or complete result.
- Invalid input produces a field or action-specific error without partial mutation. Retriable external failures preserve the user's confirmed state and expose a safe retry.

## UI and Accessibility

- Report form pre-fills safe context, warns against sensitive data, supports accessible errors/receipt, and queue shows source/report distinction.
- The complete workflow is keyboard operable, uses programmatic labels and visible focus, does not encode status by color alone, and announces asynchronous success or failure.
- Empty, loading, permission-denied, validation, provider-failure, and unavailable states have explicit copy and a safe next action.

## Acceptance Criteria

1. **F715-AC-01:** A report captures the exact safe jurisdiction, ruleset, plan revision, category, and user explanation available at submission. Finding/rule identity is required for a report about an existing finding and absent for a missing-requirement report; the latter never fabricates or misattributes one.
2. **F715-AC-02:** Submitting a report does not change any plan, finding, rule, verification status, current pointer, or user-visible regulatory claim.
3. **F715-AC-03:** Every triage mutation binds a stable request identity, committed with the transition it records under a uniqueness constraint scoped to the report it triages, and compare-and-swaps the expected immutable report version plus current triage version. A request presenting an already committed identity is resolved from that record before that comparison and returns the outcome that request originally recorded, recording no second decision and enqueuing no second downstream research; stating the scope and the ordering is what makes that recognizable, because an unscoped identity leaves the implementation to decide whether one value means the same transition across two reports, and a comparison made first rejects a retry against the triage version its own commit advanced. Success atomically records actor/time/reason, advances state/version, and enqueues any required downstream research; a recognized retry returns that result, while a mismatch changes no history, state, or downstream work and requires rebuilt triage. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. The acting actor's current authority is not among the checks the identity is resolved past: the authority this feature requires for a first attempt is re-read server-side at the replay, and the stored outcome is returned only if it still admits the operation, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.
4. **F715-AC-04:** Duplicate/link handling preserves each report and cannot inflate evidence or erase reporter context.
5. **F715-AC-05:** Unauthorized, abusive, oversized, unsafe, or cross-workspace submissions are rejected/quarantined without exposing private plan data.
6. **F715-AC-06:** Successful submission returns an opaque receipt; an authenticated reporter uses their identity, while any separately approved anonymous mode issues an additional unguessable status credential shown once. Only that reporter/credential or an authorized triage actor can retrieve bounded non-authoritative status, with no private plan, queue, other-reporter, or internal triage context. In the anonymous mode the credential is bound to a reporter-held secret or stable submission identity established before the report commits, and the same transaction that creates the report commits that binding, so a submission whose response is lost is recoverable: a retry is recognized only when it presents the stable submission identity together with the reporter-held secret that identity is bound to, and it then returns the original report's receipt rather than creating a second report or being refused as a duplicate. The reporter-held secret is this surface's current-authority check and the submission identity is not resolved past it: it is re-read at the retry and the original receipt is returned only while the binding still holds, and every authenticated read of the same report stays admitted by F715-AC-10's re-read at that operation, a replay included, on the current-authority rule `F411-AC-08` states once for this branch. The identity alone recognizes nothing and retrieves nothing, matching F715-AC-08; a retry that cannot present the matching secret is told to submit under a new identity and learns nothing about the existing report. Recovery proves possession of that secret and grants nothing an authorized retrieval would not, and an unrecognized retry remains a new report.
7. **F715-AC-07:** When the separately approved attachment mode is enabled, attachments remain in private storage; every download issuance on the authenticated path re-reads the acting actor's current authority for the report the attachment belongs to, the reporter's F-702 membership of the workspace owning the named plan or the F-703 attachment read and download permission approved for a triage actor, server-side at that issuance on the same terms F715-AC-10 states for every other authenticated operation, and rechecks scan state, and returns only a short-lived signed URL. Reporter or triage authorization stated generically is not that check: an actor holding some triage authority but no attachment read or download permission passes it and receives a URL for a file attached to a report whose text and reporter contact F715-AC-10 refuses them, and the file carries the same material. The permission on the report is not a permission on the file, and this criterion is what makes the two the same check. A signed URL is a location and not an authority; its bearer is never re-checked, so the only authorization it can carry is the one read at issuance. F-703 is PROPOSED and names no role set, so the attachment read and download permission above cannot be named; until F-703 is approved this leg is testable only as "a download URL is issued only when the acting actor holds, at that issuance and read server-side, the same authority F715-AC-10 requires for reading the report the attachment belongs to, and the attachment's scan state is safe", not against a named role or permission identifier. On the separately approved anonymous path the reporter-held secret of F715-AC-06 is that authority, on the terms F715-AC-10 states for excluding that path. Authorization loss blocks new URLs, and an issued direct-storage URL has only its disclosed bounded validity until expiry.
8. **F715-AC-08:** Every submission, authenticated and anonymous alike, carries a client-supplied submission identity, and the same transaction that creates the queue item commits that identity under a uniqueness constraint scoped to the reporting account for an authenticated report and to the approved public submission scope for an anonymous one. In that anonymous scope the submission identity alone retrieves nothing: the transaction that records the identity also binds it to the F715-AC-06 reporter-held secret, and a retry counts as the same submission only when it presents that secret, which the server verifies before returning anything. A retry presenting a known identity without the matching secret returns no receipt, no report, and no indication that the identity exists; it creates no second queue item and is not admitted as a new report under that identity, so a second reporter who guesses or deliberately collides with another reporter's identity is told to submit under a new one and learns nothing about the first. Without that binding an identity scoped to a public namespace is a bearer key, and AC-06's credential-based retrieval restriction is bypassed by replaying this criterion instead of satisfying that one. A retry presenting the same identity, and in the anonymous scope its bound secret, returns the original receipt and report, creates no second queue item, and enqueues no second triage, notification, or attachment-scanning work; a deliberately separate report sends a new identity. This is submission identity, never content uniqueness: one reporter may legitimately file two reports carrying the same category, explanation, and captured jurisdiction, ruleset, plan-revision, and finding context, so neither the payload nor the system-captured context may serve as the key, and a repeated identity is never rejected as a duplicate value. The reporter's account identity is not that key either, because the same account must be able to submit many distinct reports. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. The acting actor's current authority is not among the checks the identity is resolved past: the authority this feature requires for a first attempt is re-read server-side at the replay, and the stored outcome is returned only if it still admits the operation, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.

   On the authenticated path the reporter's verified account identity is what the submission identity is scoped to and is what proves the retry belongs to the same reporter, so no separate reporter-held secret is required and none is issued: the account credential the reporter already holds does the work the anonymous mode's secret does. The secret and its verification are therefore obligations of the anonymous scope alone, while the replay behavior, the original receipt returned, the single queue item, and the single set of downstream work are identical on both paths. F715-AC-06 is read the same way: it establishes a recoverable binding for the anonymous mode because that mode has no account identity to scope to, and it neither states nor implies that the authenticated path has nothing to replay.

   Stating that is the point of this criterion. Before it, the authenticated path, which Rollout and Fallback starts with, was the one that shipped with nothing to replay: when the submission transaction committed and its response was lost, the reporter retried and one report became two queue items and two receipts. F715-AC-04 runs after the fact and preserves each report by construction, so linking them could not undo the triage, notification, and attachment-scanning work the duplicate had already caused, and the verification team was left with two independently triageable items for one user action.

9. **F715-AC-09:** Report submission is rate limited per reporting account and per approved public submission origin. Within that limit every submission is processed as AC-01 through AC-08 describe. Once the limit is exceeded for that key, further submissions are refused before any per-submission durable write, including before the AC-08 submission-identity row and before any triage, notification, or attachment-scanning work is enqueued, and the evidence of that refused activity is one coalesced record per account, origin, and window, carrying the first and last refused instant and a count of refusals. That record is written at most once per key per approved flush interval, so the durable writes a flood produces are bounded by the number of windows and flush intervals it spans and not by the number of submissions it sends; requests arriving between flushes are refused from the limiter's own non-durable state and update no row. Between flushes the persisted last-refused instant and count are accurate as of the last flush and are read as a lower bound on refusals to date, which the record states rather than presenting as a total. The refusal is reported to the reporter with a safe next action under UI and Accessibility, and it is never reported as a received report, so a refused submission is never given a receipt or a status AC-06 would resolve.

   This criterion and F715-AC-08 are evaluated in one stated order, the same order `F411-AC-08`, `F403-AC-09` and `F306-AC-08` set out, because each otherwise assumes it owns the request. A submission presenting a committed submission identity, together with its bound secret in the anonymous scope, whose operands match under AC-08, is resolved from that record first: it returns the original receipt and report, creates nothing, enqueues nothing, and consumes no unit of this limit. The acting actor's current authority is not one of the checks that identity is resolved past: the authority that admits a first attempt, membership and permission where an organizer acts and the equivalent admission where the caller is a public or door client, is re-read server-side at the replay, and the stored outcome is returned only if it still admits the request, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. Every other submission is then checked against this limit and refused if it is exceeded, before its identity row and any triage, notification, or attachment-scanning work are committed. Only a submission passing both is recorded. Resolving the recognized replay first is what makes the two composable: enforcing the limit first would refuse the reporter whose original submission consumed the last unit and then lost its response, leaving them holding a receipt for a report they can no longer retrieve or reconcile, which is what AC-08 exists to prevent. Resolving it first discloses nothing extra, because AC-08 already requires the bound secret to be verified before anything is returned in the anonymous scope, so an identity presented without it is refused there and reaches this limit as an ordinary submission. The consequence in the other direction is stated rather than left implied: a refused submission commits no identity row, so resending that identity after the window has passed is a first submission and not a replay, and AC-08's replay guarantee covers exactly the identities that reached a committed queue item.

   The rule this applies, which the two earlier instances of the same shape on this branch also apply, is that an externally reachable surface may not persist a row or enqueue work per rejected request. A rejection must cost the caller a request and the system a bounded number of writes per key, window, and flush interval, and the check that bounds it runs before the write it bounds, never after. `F603-AC-07` states it for inbound email and `F411-AC-07` for credential validation; this criterion is the third instance, `F306-AC-08` is the fourth for public waitlist joins, and any later criterion on this branch that answers an unauthenticated or cheaply repeatable caller is subject to it. Later instances apply this rule by reference rather than restating it, so there is one formulation to change if the shape is ever wrong.

   AC-05 does not bound this: it rejects unauthorized, abusive, oversized, unsafe, and cross-workspace submissions, and the submissions a flood sends are none of those. They are well formed, in scope, under the content bounds, and sent under fresh submission identities, so AC-08 commits a durable queue item and the Jobs row's notification and attachment-scanning work for every one. AC-08's replay collapsing does not bound it either, because a flood sends distinct identities by construction, exactly as it does for `F603-AC-07`. `Privacy and security` and the API row both name rate limits without values and outside the acceptance criteria, and an implementation is built to the acceptance criteria, so the public queue this feature exists to expose is unbounded write and worker amplification until a criterion says otherwise.

   The limit, its window, the flush interval, the retention bound on coalesced records, and the bound on the set of coalescing keys are not established by any approved artifact today. They belong to the abuse controls named in the Approval Blockers, which must name all five, because an unbounded key set reintroduces the growth this bound was added to stop. Until that approval names them, this criterion is testable only as "a configured finite per-account and per-public-origin limit is enforced, submissions over it are refused before any per-submission durable write and before any downstream work is enqueued, and both the number of durable rows and the number of durable writes they produce are bounded by a finite count per key, window, and flush interval rather than growing with the submission count," not against a specific number.

10. **F715-AC-10:** Every authenticated operation this feature defines is admitted only by the acting actor's current authority, re-read server-side at that operation. A report submission on the authenticated path re-reads the reporter's current F-702 membership of the workspace owning the named plan at submission, adding to `F715-AC-05`'s cross-workspace rejection the statement of when that authorization is read; an authenticated status retrieval re-reads it at each request, on the retrieval and disclosure terms `F715-AC-06` already bounds; every triage mutation re-reads the triage actor's current F-703 authority inside the same transaction `F715-AC-03` commits, so that criterion's compare-and-swap on the report and triage versions is joined by a check on the actor it never reads; and every admin queue read, the queue, history, and duplicate-link surfaces the System Impact API row names, re-reads the actor's current F-703 triage authority per request, since no existing criterion gates them at all. `F715-AC-07` remains the rule for attachment download issuance, re-reading at each issuance the same authority this criterion requires for reading the report the attachment belongs to together with the F-703 attachment read and download permission, and is not restated here, and `F715-AC-09`'s stated order is unchanged: a recognized replay is resolved first and consumes no limit unit. A request failing the check is refused before any durable write and before any report, plan context, reporter contact, or triage history is disclosed, and its response does not distinguish a report or workspace that does not exist from one the actor may not see; the check is at the operation and not at session start, so authority removed while a request is in flight causes that request to fail rather than commit. The separately approved anonymous mode is excluded deliberately: its submission, single-show status credential, and recovery under `F715-AC-06` and `F715-AC-08` are bound by the reporter-held secret and the `F715-AC-09` rate limit by design, not by a membership the caller does not hold, and Rollout and Fallback starts authenticated and attachment-free, so the excluded surface is unreachable until its own abuse controls are approved.

    Without this criterion the existing partial checks each hold their own leg and the rest is open. `F715-AC-05` rejects a cross-workspace submission without saying when or where the authorization it presumes is read, `F715-AC-06` names who may retrieve status without requiring the check per request, and `F715-AC-03` records the triage actor and compare-and-swaps the report's versions while never reading that actor's current authority, so a triage actor whose role was revoked mid-incident still commits transitions, and the admin queue reads, which disclose reporter explanations, contact follow-up, plan context, and triage history across every workspace, are gated by no criterion at all.

    One input this criterion needs is not established by any approved artifact today and is not invented here. F-703 is PROPOSED and names no role set, so neither the triage authority nor the admin-queue read permission above can be named. Until F-703 is approved this criterion is testable only as "every authenticated submission and status retrieval is refused unless the acting reporter holds an active membership of the workspace owning the named plan, read server-side at that operation, and every triage mutation and admin queue read is refused unless the acting actor's current triage authority is confirmed server-side at that operation, with refusals disclosing nothing about whether the report or workspace exists", not against a named role or permission identifier. Naming the triage and admin-queue permissions with F-703 is an approval blocker below.

## Fixtures and Verification

- F715-AC-09 includes a replay-first fixture in which the submission that consumes the last unit of the limit loses its response and the reporter's retry with the committed identity, and its bound secret on the anonymous path, returns the original receipt and report rather than a refusal, and a fixture proving a refused submission committed no identity row so resending it later is a first submission.
- Planned automated fixture IDs are the acceptance IDs above; each must map one-to-one to a runnable test before approval can claim implementation readiness.
- F715-AC-09 includes a fixture proving that submissions beyond the configured limit are refused before any queue item, submission-identity row, or downstream job exists, that the refusals produce a bounded number of durable writes rather than one per request, and that a refused submission receives no receipt.
- Regulatory fixtures: Synthetic reports attached to approved scenario findings plus missing-requirement reports with no finding/rule identity, including wrong/missing/outdated/duplicate/abusive cases; reports are never ground truth.
- F715-AC-03 includes a fixture in which a triage transition commits, its response is lost, and the retry presenting the same request identity and the pre-transition triage version returns the original recorded outcome rather than a version-mismatch rejection, enqueuing no second research item.
- F715-AC-07 includes a fixture in which an actor holding triage authority but no attachment read or download permission is refused a download URL while a permitted actor is issued one, a fixture in which that permission is revoked between two issuances and the second is refused, and a fixture confirming that a URL issued before the revocation still resolves for its disclosed validity and that this bounded window is the documented limit of the control.
- F715-AC-10 includes a fixture in which an authenticated actor holding no membership of the workspace owning the named plan is refused at submission and at status retrieval, a fixture in which an actor holding no triage authority is refused at every triage mutation and admin queue read, each with a response that does not distinguish absence from denial, a fixture in which triage authority revoked while a transition is in flight fails that transition rather than committing it, and a paired fixture confirming the anonymous submission and credential-based status paths are unaffected.
- Security-sensitive and cross-workspace paths require negative authorization tests; provider paths require success, duplicate-delivery, retry, invalid-signature, and permanent-failure tests where applicable.
