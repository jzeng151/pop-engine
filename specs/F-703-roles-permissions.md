# F-703 · Roles and Permissions

**Status:** PROPOSED (2026-07-26) — ready for review; not implementable until approved and listed in `docs/BASELINE.md`.

**Phase:** 2 · **Issue:** [#50](https://github.com/jzeng151/pop-engine/issues/50) · **Owner:** TBD · **Reviewer:** product owner · **Approval date:** —

## Purpose and User Outcome

Workspace owners and delegated admins can grant only the access each collaborator needs, completing the authorization gate required before real user-owned data or an external beta.

## Scope

**In scope**

- Workspace roles: owner, admin, organizer, contributor, check-in staff, and viewer.
- Separate platform rules-admin authority from workspace roles.
- One server-side authorization policy layer applied to API, UI affordances, exports, uploads, jobs, and any separately approved public-token administration.

**Non-goals**

- Arbitrary custom roles, per-field ACLs, enterprise policy engines, or SSO provisioning.
- Treating hidden UI controls as authorization.

## Dependencies and Baseline

- F-701 authentication and F-702 workspaces. F-702's approved spec defines the workspace membership boundary every role change and member-management operation resolves against, and F-701 supplies the authenticated actor `F703-AC-06` reads it for; the permission matrix that check consults is the one this spec itself defines and its Approval Blockers gate. F-701 is APPROVED (2026-07-28, `docs/BASELINE.md`), and F-702 is APPROVED (2026-08-30) but unshipped. F-702's exact OpenAPI, JSON Schema, and forward migrations remain unapproved, so its approval does not make tenancy available to an F-703 implementation.
- F703-AC-08 also needs F-701 to project the provider-signed `auth_time` and support explicit reauthentication. The approved F-701 actor contract does not expose that claim today, so its amendment is an approval blocker below.
- F-702 implementation must use the membership's current role as its owner check once F-703 lands. Invitation management, removal of another member, and last-owner protection may not retain a separate owner flag or owner grant.
- Operand binding for client-supplied identities is stated locally in `F703-AC-03` and is deliberately not declared as a dependency on `specs/F-411-staff-roles-credentialed-entry.md`. Other specs on this branch take that rule by reference to `F411-AC-08`, but F-703 cannot: F-411 already declares F-703 as a dependency, because `F411-AC-09` consults the permission matrix this spec defines, so declaring F-411 here would make the two specs blockers of each other and neither could be approved first. Restating the rule locally is therefore the option taken of the three the review named, and it leaves no unapproved undeclared input in the criterion. If the rule is later promoted to an approved shared invariant, this spec and F-411 both cite that invariant and the local restatement is removed.

## Proposed authorization model

This section records the decision proposed for approval. It is not implementable while this spec remains `PROPOSED`. F-702's approval supplies behavior for review, not shipped tenancy; its exact contracts and migrations remain approval and implementation gates.

### One workspace role per membership

- The membership row is the only workspace authority source. It holds one nullable current `role` and a `role_version`. No active role-grant row, owner flag, session claim, or audit record supplies authority.
- F-702's owner membership means a membership whose current `role` is `owner`. F-702 invitation, removal, active-workspace, and last-owner checks read that same stored role. They do not read a second owner representation.
- F702-AC-09 remains the authority for the membership-backed workspace switcher and for switching active workspace context. The switcher includes every active membership whose workspace is also active, including one whose role is `null`, and returns only the minimal context needed to select it. An inactive membership or a membership of an inactive workspace is absent, cannot be selected, and is not disclosed. The exact projection remains part of F-702's machine-contract blocker and cannot include F-703 workspace detail, resource data, or another member's data. Selecting an included membership requires no non-null role. This spec's `workspace.read` permission governs only the selected workspace's detail and metadata.
- Workspace roles do not combine and do not inherit permissions from one another. Authorization reads the exact matrix cell for the membership's current role and action.
- The migration maps every existing active F-702 owner membership to `role = owner` and every other active membership to `role = viewer`. After migration, an invitation that creates a membership writes `role = viewer` and the initial `role_version` in the same transaction. A committed acceptance replay returns that row rather than creating or changing it again.
- A grant, replacement, or revoke compare-and-swaps the membership's `role_version`. A grant changes `null` to one role. A replacement changes one role to another. A revoke changes the role to `null`. Each successful operation increments `role_version` and appends history, but that history never authorizes a request.
- An active membership whose role is `null` has no role-derived workspace power, including viewing workspace detail or metadata, F-702 invitation management, and removal of another member. When its workspace is active, the switcher still includes the membership and the actor may select it under F702-AC-09, read their own membership, and leave through F-702's membership-based self-leave transition. F-702 rejects a last owner's self-leave by reading `role = owner` from that membership.
- `owner`, `admin`, `organizer`, `contributor`, `check_in_staff`, and `viewer` are distinct roles, not ranks. A change between two non-owner roles may add some permissions and remove others. The grant checks below therefore inspect both the current role and requested role rather than relying on a higher-than comparison.

### Role-change authority

| Acting role                                    | Grant when the subject has no active role                 | Replace an active role                                                                              | Revoke an active role                                                      |
| ---------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Owner                                          | Any workspace role                                        | Any workspace role with any other workspace role                                                    | Any workspace role                                                         |
| Admin                                          | `organizer`, `contributor`, `check_in_staff`, or `viewer` | Allowed only when both the subject's current role and requested role are in that same four-role set | Allowed only when the subject's current role is in that same four-role set |
| Organizer, contributor, check-in staff, viewer | Denied                                                    | Denied                                                                                              | Denied                                                                     |

An owner may change or revoke their own role only when another active owner remains after the transaction. The same last-owner check applies when an owner acts on another owner. An admin cannot act on an owner, another admin, or themself and cannot grant `owner` or `admin`. A request that would leave the current role unchanged is refused as a no-op. Every grant, replacement, and revoke still follows the version, replay, actor-authority, workspace-binding, and audit requirements in F703-AC-03, F703-AC-06, and F703-AC-07.

Only owners and admins may read the full member list and role-change history. Only owners and admins may read workspace authorization audit records. No workspace role may grant or revoke the platform rules-admin role.

### Recent authentication for authority changes

- Every workspace grant, replacement, or revoke requires a provider-signed F-701 `auth_time` where `0 <= transaction_time - auth_time <= 10 minutes`. The server reads its own transaction time. It rejects a missing, stale, malformed, or future `auth_time`. Refreshing a session token does not reset `auth_time`; the actor must authenticate again with an approved F-701 method.
- The server checks recent authentication on the first attempt and every replay. It checks again in the same transaction that reads the actor's membership role and commits the role change. The self-change replay exception in F703-AC-03 does not skip this check.
- A recent-auth failure returns only that recent authentication is required. It does not disclose whether the workspace, subject membership, current role, requested role, request identity, or stored outcome exists. It changes no membership, role, request-identity, or audit row and makes no provider call. A redacted operational security log may record the actor, request correlation ID, and failure category.
- The deployment-only platform-role command requires both its dedicated database operator credential and a provider-signed F-701 proof whose subject equals the configured product-owner operator actor and meets the same 10-minute rule. The proof belongs to the operator, not necessarily the target actor. A missing, stale, or wrong-subject proof prevents the command from reading or changing any platform grant or returning a stored replay outcome.

### Platform rules-admin authority

- Platform rules-admin is a separate versioned grant keyed to the F-701 actor. It is not a workspace membership or workspace role. Holding it grants no workspace action in the matrix above, and holding a workspace role grants no platform action.
- The platform permission covers rules-admin source and configuration reads, comparison creation, comparison-result reads, previews, exports, generated reports, and approved publication operations. Every such operation checks the current platform grant when it produces or returns data.
- The role authorizes a platform operation but cannot approve regulatory content, a verification promotion, or a ruleset publication. Those decisions still require the product owner's recorded approval under documentation governance.
- F-703 adds no public or workspace-facing platform-role endpoint. The product owner grants or revokes the role through one deployment-only administrative command running under a dedicated database operator credential. The runtime API database role cannot invoke that command or write platform grants directly.
- The command takes the target F-701 actor ID, `grant` or `revoke`, the expected grant version, the target role, a stable client request identity, a reason, and the recent-auth proof above. The target role is `rules_admin` for a grant and `null` for a revoke. The request identity is unique within the deployment command and binds the operation, target actor, expected grant version, target role, reason, and configured operator actor. Reuse with any different operand is a conflict that returns no stored receipt or grant data and writes no grant, request identity, or audit record.
- On every first attempt and replay, the command validates the dedicated database credential and rechecks that the fresh F-701 proof belongs to the currently configured product-owner operator before it reads a request identity or platform grant. Once that check passes, it looks up a committed request identity before comparing the expected grant version. A matching replay returns the immutable receipt recorded by the original command and appends no second audit entry. A request with no committed identity must compare-and-swap the exact expected version; a stale version writes no request identity, grant, or audit entry.
- A successful first attempt atomically changes the current grant, increments its version, records the immutable request receipt, and appends one redacted audit entry. The receipt describes that historical command and is never presented as the target actor's current platform authority. A separate deployment-only current-grant read rechecks the same current operator credential and recent-auth proof and reads the current grant directly. Only the product owner operates these deployment commands. The grant command is also the bootstrap path for the first rules admin.
- Revocation blocks the next platform operation and every later read or export of a retained result. A rules admin cannot grant or revoke platform authority merely by holding the role.

### Queued and provider work

- A user-initiated workspace job records the initiating F-701 actor, owning workspace, subject aggregate, and exact permission that admitted creation. It stores no client-supplied role claim.
- The worker re-reads that actor's active membership and permission when claiming the job. It re-reads them again immediately before the protected database write or provider handoff. A changed role may continue the job only when the new role still allows the recorded permission.
- The execution-time check and side effect use the authorization fence selected by the approved PostgreSQL job/outbox ADR required by `ARCHITECTURE-FUTURE.md` §18 item 3. If revocation wins, the worker makes no protected write and no provider call. If the side effect wins, the later revocation observes that order and does not report the side effect as stopped.
- Reminder jobs created by `checklist.materialize` recheck that permission for the actor who materialized the checklist. The synchronous test-alert endpoint rechecks `alert.test` immediately before its provider handoff. A platform job rechecks the separate platform grant instead of a workspace role.
- An authorization denial records the actor, workspace, job, required permission, and denial reason without contact data, document contents, secrets, invitation tokens, or provider credentials. The reviewed job contract chooses the terminal job state; this spec requires only that denial cannot look successful and cannot retry into a side effect without a newly authorized request.

## Inputs, Outputs, State, Validation, and Errors

- Inputs are a grant, replacement, or revoke request by an owner or the bounded admin cases in the matrix, with the exact expected membership version and `role_version`. Output is an immutable operation receipt recording the role state that commit produced. It is not a current-authority read; any API or UI that presents the membership's current role reads that membership separately under the current authorization policy.
- The deployment-only platform input is the authenticated operator, operation, target actor, expected grant version, target role, reason, and stable request identity. Its output is the immutable receipt for that command. The separate current-grant read is the only operator output that presents current platform authority.
- The membership's current role is one role or `null`, and every change increments `role_version`. Authorization changes take effect on the next request and, for a queued job, at both the claim check and the execution-time recheck that immediately precedes the job's side effect. Stale privileged context is invalidated.
- Unknown actions, missing membership, missing workspace, a null role, and stale membership or role versions deny by default. Platform rules-admin checks never derive from a workspace role.
- Missing or unresolved material data stays visibly unset, unknown, pending, or failed as appropriate; it never becomes a successful or complete result.
- Invalid input produces a field or action-specific error without partial mutation. Retriable external failures preserve the user's confirmed state and expose a safe retry.

## UI and Accessibility

- Member management explains each role in plain language and never offers a grant the current actor cannot make.
- A stale recent-auth response sends the actor through explicit F-701 reauthentication and then rebuilds the role-change review from current membership and role versions. The browser does not submit the stored change automatically after reauthentication.
- The complete workflow is keyboard operable, uses programmatic labels and visible focus, does not encode status by color alone, and announces asynchronous success or failure.
- Empty, loading, permission-denied, validation, provider-failure, and unavailable states have explicit copy and a safe next action.

## Acceptance Criteria

1. **F703-AC-01:** Every `Allow` cell in the approved permission matrix has a same-workspace allow test and an inactive-membership or cross-workspace deny test. Every blank cell has a same-workspace deny test. No role/action pair relies on an untested default. Every named role may read workspace detail and metadata through `workspace.read`; a `null` role may not. That permission is never an added prerequisite for a different matrix action. F702-AC-09's switcher includes every active membership whose workspace is active with only its minimal selection context, including when the membership's role is `null`. It excludes an inactive membership and a membership of an inactive workspace; neither excluded target can be selected or disclosed. Selecting an included membership occurs before role policy runs.
2. **F703-AC-02:** A client cannot gain authority by changing a workspace ID, role value, URL, hidden form field, queued job, or public token.
3. **F703-AC-03:** Every grant, replacement, or revoke mutation requires the subject membership to be active and compare-and-swaps the exact expected membership version and `role_version` on that membership. The transaction locks and re-reads the subject's active state and versions, then atomically writes the new current role and incremented `role_version` on that same row. An absent or removed subject and a version mismatch change no authority, request identity, or audit history. They return the same non-disclosing refusal and require rebuilt review. A revoke writes `role = null`, which removes all role-derived authority while leaving F-702 self-leave available. An owner replacement or revoke also uses F702-AC-04's serialized workspace invariant, reading `role = owner` from memberships so concurrent changes cannot remove the last owner. No separate role-grant or owner record participates in any check.

   Role revocation prevents a stale concurrent grant, the next privileged request, and any queued job from committing its protected write or provider handoff. A claim-time check alone does not deliver that because a revocation may commit while a worker holds its lease. The job rechecks the actor's current membership role and `role_version` at execution, immediately before the irreversible side effect. The approved PostgreSQL job/outbox ADR must define the authorization fence that gives the revocation and side effect one observable order. If revocation wins, the job cannot cross the handoff. If the handoff wins, revocation observes that order rather than reporting queued work as stopped. Denials cause no provider side effect or data disclosure and are recorded without secret or contact content.

   Every grant, replacement, and revoke also commits its own stable client-supplied request identity, under a uniqueness constraint scoped to the membership it changes, in the same transaction as the role change and audit entry. A request presenting an already committed identity is resolved from that record before the membership and role-version comparison above and returns the immutable operation receipt that request originally recorded, changing no authority a second time and appending no second audit entry. That receipt describes the committed operation and is never presented as the membership's current authority. If an API response or UI also presents current authority, it obtains it through a separate, currently authorized membership read after resolving the replay. It is not resolved past the subject membership's current active state, the acting actor's current authority, or the recent-auth check. The transaction re-reads all three at replay and returns the stored receipt only if all three still admit the request. The one authority exception is the role that same commit removed from the acting actor; that commit satisfies the role read rather than failing its replay, but it does not satisfy recent authentication.

   The identity is committed with the request fields that determine its recorded result, at minimum the workspace, subject membership, requested role change, expected membership version, and expected `role_version`. A later request presenting the same identity with any different operand is refused as a conflict, changing no authority and returning no stored outcome. The identity is still the key and the operands are only a precondition on reusing it, so this is not content uniqueness: two genuinely distinct role changes that read the same are both committed. This rule is stated here in full rather than by reference to `F411-AC-08`, which states the same rule once for the specs that depend on F-411; the Dependencies section explains why this spec cannot take that reference.

   Without the request identity, comparison and safe retry contradict each other on the same request. When a revoke commits and its response is lost, the retry still names the membership version and `role_version` the administrator read, which that commit advanced. Rejecting it as a mismatch tells the administrator the revoke failed when it succeeded and invites unnecessary follow-up changes and audit entries.

4. **F703-AC-04:** Rules-admin functions require the separate platform role and cannot be granted by a workspace owner. A rules-admin function is any operation on a platform rules-admin surface, and reading one is a rules-admin function exactly as much as writing one: source and configuration read, comparison creation and result read, preview, export, generated report, and approved publication each hand ruleset source, verification, and configuration internals to whoever receives them, so each is admitted only by that role, checked server-side at the operation that produces or returns the data rather than at session start or from a client-supplied role claim, and a refusal discloses nothing about which artifacts, versions, or checksums exist. Authority lost after a result is produced blocks every later read and export of it, including a retained one.

   The deployment command follows the request-identity contract in the platform-authority section above. Current deployment-operator authorization and recent authentication are rechecked before request or grant data is read. A committed matching identity is resolved before the expected grant version and returns its immutable historical receipt without another write or audit entry. Different bound operands are a non-disclosing conflict. An uncommitted identity with a stale expected version writes nothing. A successful first attempt changes the current grant, records its receipt, and appends one audit entry atomically. Any current-grant display comes from the separate currently authorized grant read, never from a replay receipt.

   The read half is stated here because the authority rules on this branch were written around operations that commit. F702-AC-10 quantifies over "every mutation of a workspace-owned aggregate, and every externally initiated callback", F410-AC-08 and F714-AC-09 attach their re-read to the transaction that performs a compare-and-swap, and the paragraph of F702-AC-10 that carries the rule across to platform scope still phrases the obligation as validation "at the moment of the write". A surface that only reads has no commit to attach any of them to, so it satisfied all of them vacuously. `F704-AC-04` already applies this rule to platform-scoped activity; `F606-AC-10`, `F712-AC-07`, and `F713-AC-07` apply it to the three rules-admin surfaces whose criteria never named this spec at all. Platform rules-admin authority never derives from a workspace role, per the deny-by-default state rule above, so naming a workspace, holding any workspace role, or owning a workspace admits nothing on those surfaces.

5. **F703-AC-05:** The proposed production-gate runbook below is normative acceptance behavior, not release advice. It consumes the separately approved policy and ADR values named in the runbook and Approval Blockers; approval of this spec cannot select those values. The product owner may explicitly enable the joint F-701, F-702, and F-703 production gate only when every numbered runbook row records a passing result on the exact deployed commit and migration head. A whole-gate row passes only through its enabled control proofs. A conditional row passes either through its enabled-path allow, deny, replay, and revocation proofs or through the row's explicit fail-closed disabled proof. Disabling a conditional feature is a tested release state, not an exception. No disabled proof can satisfy missing identity, tenancy, membership-authority, recent-authentication, browser-authentication, core rate-limit, or cross-workspace controls. A failure in any of those controls keeps the joint gate closed. The release record carries every result and the enabled or disabled state of each conditional feature.

6. **F703-AC-06:** Every grant, replacement, and revoke names the workspace and subject membership it acts on. The transaction re-reads the acting actor's current membership row and current role for that workspace and admits only the exact role change the approved authority table allows. It serializes against a concurrent change to the actor's own membership role, so the actor's revoke and the actor's attempted grant cannot both commit. F703-AC-03 supplies the subject membership and `role_version` comparison, request replay, and queued-job recheck.

   Every full-member-list, role-history, authorization-audit, and member-management read likewise re-reads the actor's current membership role on every request. A failed check occurs before any durable write or protected disclosure and returns the same response for an absent record and a record the actor may not see. F702-AC-04 reads the same membership role for the serialized last-owner invariant. F703-AC-04 keeps platform authority separate.

   Without this criterion, the subject comparison in F703-AC-03 can pass for an actor whose own role was revoked or never allowed the change. The matrix and parameter-tampering rule do not establish that the transaction read the acting actor's current authority.

   The proposed matrix now names every granting and member-management authority this criterion checks. It remains an unapproved input until the product owner approves this spec. Before that approval, no implementation may treat the proposed cells as authority.

7. **F703-AC-07:** The subject membership a grant, replacement, or revoke names must resolve to the workspace that same request names, compared server-side inside the transaction that commits the change and before the subject membership is read for update. `F703-AC-06` re-reads the acting actor's authority for the named workspace and `F703-AC-03` compare-and-swaps the subject membership's own versions, and the two are independent: the workspace and the subject membership arrive as separate request fields, so an actor holding an active membership of workspace A and a membership of workspace B names workspace A and a subject membership in B and passes both. The actor is legitimately authorized where they stand, the named subject membership genuinely exists and its versions are current, and the mutation commits, so a role in another organization's workspace is granted, replaced, or revoked by an administrator who holds no authority there at all. A mismatch refuses the whole request before any durable write, changes no membership role, appends no audit entry, and returns the same non-disclosing response `F703-AC-06` requires, which does not distinguish a workspace or membership that does not exist from one the actor may not see.

   This applies approved `F702-AC-10`'s fourth obligation, which states once for the whole feature set that every record an operation names must resolve to one workspace, to the pair this criterion's own mutations name. It is stated here so the F-703 mutation names that comparison directly. `F702-AC-11` M-04 delegates the whole role-change transition to whatever F-703 approves, so no criterion outside this spec supplies the comparison either, and `F702-AC-04`'s last-active-owner invariant is evaluated for the subject membership's own workspace, which with this criterion in force is the named one.

   F-702 now approves the membership-to-workspace behavior this criterion needs, but it remains unshipped and its exact contracts and forward migrations remain unapproved. Until those contracts and migrations are approved and F-702 ships, this criterion is reviewable only as "a grant, replacement, or revoke whose named workspace and named subject membership do not resolve to the same workspace is refused, changes no authority, appends no audit entry, and discloses neither"; F-703 may not treat tenancy records as available runtime inputs.

8. **F703-AC-08:** Every workspace grant, replacement, or revoke and every deployment-only platform-role grant or revoke enforces the 10-minute recent-auth rule above on the first attempt and replay. A missing, stale, malformed, or future provider-signed `auth_time` fails closed before any protected record is read or changed. The response discloses only that reauthentication is required, commits no request identity or audit entry, and returns no stored replay outcome. A fresh proof still needs every authority, scope, version, last-owner, and operand check in the other criteria.
