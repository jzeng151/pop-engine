## User Story

As an independent organizer, I can see which published rules snapshot produced my plan, each requirement's verification state, and where it comes from, so I can judge the output and know its shelf life.

## Inputs

- `GET /api/rules/meta` → `{ruleset_version, snapshot_date}` from the loaded rules file.
- Per-line immutable `sources` snapshot (citation + every URL), primary `source_url`, `verification_status` (the badge value; canonical, NOT NULL, constrained), and nullable `last_verified_date` on `permit_plan_items`. A date is stored only when every contributing published rule provides one; a finding merged from multiple rules uses the earliest contributing date, otherwise it stores null. (The nullable `verified_status` column is a deprecated duplicate, do not use it; see ARCHITECTURE and issue #76.)

## Outputs

- A banner on every plan view: "Rules snapshot nyc.v2.9 · published July 29, 2026". Never "verified as of" — a snapshot date means published-on, not all-facts-verified-on.
- Per-line verification-status rendering plus either citation click-through or the explicit not-covered-by-this-ruleset-version COVERAGE_GAP state.
- Per-line "last verified" date only when the immutable plan item stored one; never substitute the ruleset snapshot date.

## Acceptance Criteria

1. The banner renders on every plan and checklist view, populated from stored data and never from hardcoded copy. A checklist's top banner names its current plan. If a retained row comes from a different snapshot, that row also shows its originating `ruleset_version` and `snapshot_date`; rows from the current snapshot do not repeat the banner. AC 4 names which stored data: a view with a plan in context reads that plan's row, so this criterion is about never hand-writing the version or date into the markup, not about reading the live file.
2. Every plan line shows its verification status. A source-bearing line shows its citation; a COVERAGE_GAP line that carries no citation visibly states that the combination is not covered by this ruleset version, and that the plan may therefore be incomplete, rather than inventing a citation. It must NOT say or imply that a source is missing or pending: that is RESEARCH_REQUIRED's meaning, and the published legend in `rules/nyc-rules.v2.9.json` defines COVERAGE_GAP as "combination not modeled by this ruleset version; advisory asserts nothing", which asserts nothing about sources at all. RESEARCH_REQUIRED renders "confirm with agency" visibly (not hidden in a tooltip), and OFFICIAL_CONFLICT lines render both readings with both sources.
3. Clicking a citation opens the source URL; lines whose portal/source URL is still unresolved render the citation text without a dead link.
4. The plan's pinned `ruleset_version` **and `snapshot_date`** are shown (both from `permit_plans`, not from the live file), so an old plan viewed after a rules update displays the version that produced it and the publication date that version carried. The two travel together: showing a pinned version beside the live file's date would render a pair that never existed. `GET /api/rules/meta` remains the live file's values and is for surfaces with no plan in context; it is not the plan banner's source.
   **Legacy plans:** a plan generated before migration 002 has a null `snapshot_date`. The banner renders the pinned version and says the publication date was not recorded for that plan — it never falls back to the live file's date, which would pair a pinned version with a date it never carried, and it is never backfilled, because the plan does not record which artifact it read and a derived date would assert provenance nothing witnessed. The version alone is still the honest answer to "which rules produced this".
   **Mixed checklists:** each row reads the source plan exposed by F-202 Acceptance Criterion 8, and never the live rules file. Which plan that is depends on whether the row is **struck through**, because a row's provenance names the plan its displayed values came from: the pair has to be one that existed.
   - A **struck-through** row keeps the dates of the last plan that raised it **as this row's task** and is attributed to that plan, which is its persisted plan item. Never the checklist's current plan.
   - A row that is **not struck through** is attributed to the latest plan. That plan raised it too, since a surviving requirement is raised by every plan that includes it, and it is the plan whose recalculated dates the row displays (PRD principle 6). Attributing it to the persisted item instead would print a version beside recalculated dates it never produced, which is the pair this criterion forbids.

   **Keyed to struck-through-ness, not to why the row was struck.** An earlier revision keyed the first case to the requirement having been dropped, "struck through because the latest plan no longer raises it". That question cannot identify a struck row, which is the whole of the defect: whether the latest plan raises something is a fact about the latest plan, and whether a row is struck through is a fact about the row. F-202 Acceptance Criterion 9's terminal clause separates them by making "still raises" apply only to a row that has not been struck through. The situations below follow from that separation; they are not a list this criterion has to keep complete, and each states its own facts rather than sharing a premise:
   - a row struck through by a **kind change** is struck as one the latest plan no longer raises, because a requirement is its rule-id set AND its kind, and it keeps the values and attribution it had. The earlier key reaches this row only when "no longer raises it" is read with that identity; read as the rule-id set alone it sorts the row into the second case, which is one way the old key failed.
   - that same row after the kind **returns** is the only situation in which a struck row stands beside a latest plan raising the same rule-id set AND the same kind. It is terminal and is never re-pointed, so the returning requirement is a new appended row, unstarted and not struck, which takes the second case above on its own account. Here the earlier key failed on any reading, because the row is struck and the requirement is raised.

   **This provably changes nothing for any row that could exist before that clause, which is checkable rather than a claim about simplicity.** Until Acceptance Criterion 9 gained its terminal clause, the only way a row became struck through was F-202 Acceptance Criterion 6 striking what the latest plan no longer raises. On that row space the two keys are the same predicate, in both directions: struck through if and only if the latest plan no longer raises it, and not struck through if and only if it does. So every such row selects the same case and gets the same answer under either key, the old one and this one. No case is introduced and no outcome moves; the only row the two keys disagree about is the terminally struck one, which is the row that previously fell between them and could not exist before the clause that creates it.

   So the two cases are unchanged in what they decide and changed in what selects them. Struck-through-ness is a two-valued fact about the row, which makes the pair exhaustive by construction; that holds whether the value is stored or computed, and today it is computed rather than stored, since no migration creates a strike column. "Why it was struck" is a list of circumstances, and this criterion has now been extended once because such a list was complete only until the lifecycle grew. A third case for the terminal row was the alternative and is refused for that reason: it would decide the same thing the first case already decides, keyed on a circumstance rather than on the state, and would leave the next lifecycle question needing a fourth. This agrees with F-202 Acceptance Criterion 9 rather than restating it: that criterion defines "still raises" as applying only to a row that has not been struck through, and owns the lifecycle, including that dropping is one-way and that a struck row is not re-pointed by a review. What is F-206's is only which plan a row's displayed values and provenance are read off, and on that the answer for every struck-through row is the same one.

   The implementation does not match: struck-through-ness is currently derived from whether the latest plan holds an item for the same rule-id set, so a terminally struck row reads as not struck through at all, is treated as live, and is attributed to the latest plan. That derivation is the predicate both criteria were re-keyed away from, which is why the gap is not a detail of wiring: the code has no independent notion of a struck row to select on, and nothing in the schema stores one. Bringing the code to this criterion is not a spec change and is not made here.

   Written as two cases because conflating them produced SPEC-CONFLICT #115. The earlier wording said a retained row is _never_ attributed to the current plan, which is true of a dropped row and false of a still-required one, and that was the only sentence the two readings actually collided on. F-202 Acceptance Criterion 8 agrees once read on its own terms: its "last plan that raised it" is the latest plan for a requirement that survives, and its purpose clause, never copied from the live rules file and never duplicated into checklist storage, guards the same thing this criterion does. That wording was given the same terminal-lifecycle treatment on PR #132, now merged, and it reached the same key independently: AC 8 selects on whether a row is struck through rather than on whether the latest plan raises the requirement. The two criteria therefore agree on the record from both sides rather than one deferring to the other, and what this criterion relies on is AC 8's purpose clause, which that amendment left untouched. Its "through its existing plan-item relationship" describes where the values are found, not a rule that provenance must lag them. In both cases above the values and the provenance are read off one object, so neither can print a pair that never existed.

5. A missing `last_verified_date` renders no date and no implied verification date; snapshot publication date and per-line verification date remain distinct.
6. Demo check: the banner is visible in every screen of the demo path (DESIGN.md demo plan step 5 includes a live citation click-through).

## Edge Cases

- Live ruleset version ≠ plan's pinned version (post-MVP rule update): banner shows the plan's version plus "a newer ruleset exists; regenerate to update". (Cheap now; required later by F-503/F-713.)
- Citation present but source URL unresolved: render citation text without a link.
- COVERAGE_GAP carrying no citation: render the status plus "Not covered by this ruleset version. This plan may be incomplete for your event.", with no citation link. The string is held in `apps/web/app/verification-copy.ts` and tested against RESEARCH_REQUIRED's rendering so the two cannot converge.
