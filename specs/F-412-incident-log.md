# F-412 · Incident Log

**Status:** PROPOSED (2026-07-26) — ready for review; not implementable until approved and listed in `docs/BASELINE.md`.

**Phase:** 3 · **Issue:** [#44](https://github.com/jzeng151/pop-engine/issues/44) · **Owner:** TBD · **Reviewer:** product owner plus affected architecture, contract, security, and lane owners (TBD) · **Approval date:** —

## Purpose and User Outcome

Authorized event staff can record timestamped incidents and private attachments while preserving corrections and avoiding unsupported legal or emergency classifications.

## Scope

**In scope**

- Create timestamped incident entries with author, description, approved category/severity if defined, attachments, and follow-up notes.
- Append corrections/addenda and preserve original records.
- Filter/export only under approved role and retention rules.

**Non-goals**

- Emergency dispatch, medical records, law-enforcement reporting, legal conclusions, automated severity, or public disclosure.
- Editing or deleting original history outside the approved retention/legal process.

F-702 supplies the workspace membership boundary the incident and its event resolve against and F-703 supplies the permission matrix `F412-AC-10` checks; F-701 supplies the authenticated actor both read from. - Operand binding and replay ordering for client-supplied identities: `specs/F-411-staff-roles-credentialed-entry.md` F411-AC-08 states once, for this whole branch, that a client-supplied identity is committed with the operands that determine its recorded result and that a reuse carrying different operands is a conflict rather than a replay, and that a committed identity is resolved before any version, generation, state, or limit check whose answer the committed operation itself changed, while the acting actor's current authority is re-read at the replay and must still admit the operation before any stored outcome is returned. Every identity criterion below relies on it. F-411 is PROPOSED, so that rule is not an approved input today and this spec is not implementable against it until F-411 is approved or the rule is promoted to an approved shared invariant; F411-AC-08 records both paths.

## Inputs, Outputs, State, Validation, and Errors

- Inputs are staff-confirmed event/time/description, optional safe files, and a stable request identity on each create, each addendum append, each standalone attachment upload, and each export creation; outputs are append-only incident and addendum records, private attachment records, plus the pinned export job and artifact.
- State is recorded with later addenda/correction markers; unsafe attachments remain quarantined and separate from incident status.
- The event's incident-export source generation advances on any incident, addendum/correction, or retention removal; every queued or staged export pins that generation.
- Unknown time/category or conflicting accounts remain explicit and are not reconciled by the system.
- Missing or unresolved material data stays visibly unset, unknown, pending, or failed as appropriate; it never becomes a successful or complete result.
- Invalid input produces a field or action-specific error without partial mutation. Retriable external failures preserve the user's confirmed state and expose a safe retry.

## UI and Accessibility

- Fast event-day entry supports keyboard/mobile use, visible saved state, safe cancel, attachment progress, and clear emergency-service disclaimer/action copy.
- The complete workflow is keyboard operable, uses programmatic labels and visible focus, does not encode status by color alone, and announces asynchronous success or failure.
- Empty, loading, permission-denied, validation, provider-failure, and unavailable states have explicit copy and a safe next action.

## Acceptance Criteria

1. **F412-AC-01:** An authorized staff member records staff-confirmed occurrence time separately from immutable server recorded-at time/actor and retrieves the incident only inside the correct event/workspace. Occurrence time may be explicitly unknown; both values are displayed without substituting one for the other. The create request carries a client-generated request identity, and the creating transaction commits it under a uniqueness constraint scoped to the event, so a retry after a lost response returns the original incident rather than appending a second one that would then read as a separate occurrence in history and exports. A deliberate second entry sends a new identity. Uniqueness over the payload is not that enforcement: two genuinely separate incidents may carry identical event, time, and description values, so it would refuse a real record. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. The acting actor's current authority is not among the checks the identity is resolved past: the authority this feature requires for a first attempt is re-read server-side at the replay, and the stored outcome is returned only if it still admits the operation, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.
2. **F412-AC-02:** Correction or follow-up appends a timestamped addendum and cannot rewrite the original account. The append request carries its own client-generated request identity, and the transaction that appends the addendum commits that identity under a uniqueness constraint scoped to the incident, so a retry after a lost response returns the original addendum instead of appending the same historical statement twice and advancing the incident-export generation a second time. AC-01's identity does not reach this case: it is scoped to incident creation and says nothing about later appends. A deliberate second addendum sends a new identity. The append request also names the incident's current retention and availability generation, the same generation F412-AC-07 advances and F412-AC-09 compare-and-swaps, and the transaction that appends the addendum compare-and-swaps it, so retention removal and an in-flight append have exactly one winner on the same terms as an attachment upload. 3. **F412-AC-03:** Unknown/conflicting details remain labeled and the system never generates a legal, medical, or emergency classification.
4. **F412-AC-04:** Unauthorized, unsafe, oversized, or mismatched files remain unavailable and do not erase the text incident. The size and type bounds are the ones the upload handling named in the Approval Blockers establishes; until it is approved this criterion is testable only as "configured finite size and type bounds are enforced against the file's verified bytes and a file outside them is rejected," not against a specific number or type list.
5. **F412-AC-05:** Export/retention behavior matches the approved policy and records the actor/action.
6. **F412-AC-06:** Attachments remain in private storage; every download issuance re-reads the acting actor's current F-702 membership of the workspace that owns the incident's event together with the F-703 attachment read and download permission approved for the action, server-side at that issuance on the same terms F412-AC-10 states for every other operation, rechecks scan state, and returns only a short-lived signed URL. Membership is not the check on its own: a member holding no attachment read permission passes a membership-level recheck and receives a URL for a file attached to an incident record whose text F412-AC-10 refuses them, and F412-AC-07 already states the export leg at the stricter event/workspace-role level, so leaving this leg at bare authorization makes the attachment the weakest path to the same incident. A signed URL is a location and not an authority; its bearer is never re-checked, so the only authorization it can carry is the one read at issuance. F-703 is PROPOSED and names no role set, so the attachment read and download permission above cannot be named; until F-703 is approved this leg is testable only as "a download URL is issued only when the acting actor holds an active membership of the workspace owning the incident's event, read server-side at that issuance, and the attachment's scan state is safe", not against a named role or permission identifier. Authorization loss blocks new URLs, and an issued direct-storage URL has only its disclosed bounded validity until expiry.
7. **F412-AC-07:** Generated exports remain private and pin the complete incident/addendum/retention generation they read. A generation change cancels queued work, invalidates staged artifacts, and blocks new access to the obsolete export. Every authenticated stream or short-lived signed URL issuance rechecks that generation and re-reads the acting actor's current F-702 membership of the workspace that owns the incident's event together with the F-703 incident export and download permission approved for the action, server-side at that issuance on the same terms F412-AC-10 states for every other operation. Event and workspace role are not the check on their own: a same-workspace member who holds no incident export or download permission passes an authorization stated at that level and receives the stream or URL for the full incident and addendum bundle while F412-AC-10 is refusing them export creation and the incident text the bundle contains, so leaving this leg at generic role authorization makes the generated export the weakest path to the same incident, as F412-AC-06 already states for the attachment leg. A signed URL is a location and not an authority; its bearer is never re-checked, so the only authorization it can carry is the one read at issuance. F-703 is PROPOSED and names no role set, so the incident export and download permission above cannot be named; until F-703 is approved this leg is testable only as "a stream or download URL is issued only when the acting actor holds an active membership of the workspace owning the incident's event, read server-side at that issuance, and the pinned generation is still current", not against a named role or permission identifier. An already issued direct-storage URL has only its disclosed bounded validity until expiry.
8. **F412-AC-08:** Creating an export binds the request to a stable client-supplied request identity, committed with the export job under a uniqueness constraint scoped to the event. A retry presenting the same identity returns the original job and, once complete, its original artifact, enqueues no second job, and stages no second artifact; a deliberately separate export sends a new identity. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.

   F412-AC-07 pins the source generation and access state, which guards freshness rather than replay: a retry reads the same generation and passes both checks. F412-AC-01's and F412-AC-02's identities do not reach this case either, because each is scoped to one incident create or one addendum append and says nothing about exports. When the create transaction commits and its response is lost, the retry stages a second private artifact of the same incident and addendum records, which is a second copy of sensitive incident data in storage, a second retention clock, and a second F412-AC-05 actor/action record for one authorized export.

9. **F412-AC-09:** Adding an attachment to an existing incident binds the request to a stable client-supplied request identity, committed with the attachment record under a uniqueness constraint scoped to the incident. A retry presenting the same identity returns the original attachment record, stores no second copy of the bytes, and repeats no scan; a deliberately separate attachment sends a new identity. An attachment supplied inside the create request is committed with the incident under F412-AC-01's identity and needs no second one. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch: it is committed together with the request fields that determine the recorded result, including every aggregate, version, and generation the request names, and a later request presenting the same identity with any different operand is refused as a conflict rather than being answered with the stored result. The identity is still the key and the operands are only a precondition on reusing it, so this is not the content uniqueness this criterion already forbids. That identity is resolved in the order `F411-AC-08` states once for every client-supplied identity on this branch, applied here rather than restated: a request presenting an already committed identity is resolved from that record before the version, generation, state, and limit checks this criterion requires, and returns the outcome that request originally recorded, because the commit the retry repeats is exactly what moved the state those checks read. A request whose identity resolves to no committed outcome is then held to every one of them, and a request refused by one of them commits no identity, so re-presenting it later is a first attempt and not a replay.

   The request also names the incident's current retention and availability generation, the same generation F412-AC-07 advances, and the transaction that creates the attachment record compare-and-swaps it. Removal under F412-AC-05 and an in-flight upload therefore have exactly one winner: a removal that commits first advances the generation, and the upload is rejected in full against the generation it did not see, storing no bytes, creating no attachment record, and starting no scan; an upload that commits first is complete before the removal reads the generation, so the removal acts on a set that includes it and removes it with the rest. A rejected upload discloses only that the incident's retained data is no longer available, per F412-AC-06's authorization and scan-state rechecks, and the staff member's recovery is to reload the incident rather than to retry the same request.

   Without that comparison the two writes are unordered and the removal loses silently. F412-AC-09 compares only the upload's own request identity, which a first attempt satisfies by construction, and F412-AC-07 advances the generation to invalidate exports rather than to serialize this write, so an upload in flight when retention removal commits stores sensitive bytes and creates a new attachment record for an incident whose retained data was just removed. Nothing afterwards notices: F412-AC-06 issues download URLs for it because it is a real attachment record with a real scan state, and F412-AC-05's actor/action record says the removal succeeded. The result is retained incident data that the approved retention policy has already ordered destroyed, held under a record that looks correct.

   The API lists attachment as its own operation, and the identities already in this spec are each scoped elsewhere: F412-AC-01's covers one incident create, F412-AC-02's one addendum append, F412-AC-08's one export creation. None reaches a file staff attaches to an incident that already exists, so a lost response on that upload lets the retry store and scan the same sensitive file a second time and show two attachment records for one action. This is request identity, never content uniqueness: two genuinely different photographs of the same scene may be uploaded seconds apart, and staff may deliberately attach an identical file twice, so neither the bytes nor a digest of them may serve as the key, and a repeated identity is never rejected as a duplicate value. F412-AC-04 rejects an unauthorized, unsafe, oversized, or mismatched file before it is stored, so a rejection commits no identity and a later attempt is a fresh upload rather than a replay.

10. **F412-AC-10:** Every operation this feature defines names the incident's event and the workspace that owns it, and is admitted only by the acting actor's current F-702 membership of that workspace together with the F-703 permission approved for the action, both re-read server-side from stored membership and role at the moment of the operation and, for a write, inside the same transaction that commits it. The existing rechecks remain the rule for their legs and this criterion composes with them by name: F412-AC-06 stays the recheck of that same current membership, the F-703 attachment read and download permission, and scan state at attachment download URL issuance, F412-AC-07 stays the recheck of the pinned generation, that same current membership, and the F-703 incident export and download permission at export stream and URL issuance, and F412-AC-01's scoping clause stays the statement that an incident is retrievable only inside the correct event and workspace, which this criterion supplies the actor check for. This criterion covers everything else: incident creation under F412-AC-01, inside the transaction that commits the incident and its request identity, addendum append under F412-AC-02, standalone attachment upload under F412-AC-09, export creation under F412-AC-08, incident query and filter reads, and the retention and export actions F412-AC-05 records, whose behavior stays deferred to the approved policy while the actor performing them is gated here. A request failing the check is refused before any durable write and before any incident, addendum, attachment, or export is disclosed, and its response does not distinguish an incident or event that does not exist from one the actor may not see. The check is at the operation and not at session start or workspace switch, so authority removed while a request is in flight causes that request to fail rather than commit.

    Without this criterion the issuance rechecks are the only actor checks in the spec, and they run after the sensitive writes rather than before them. AC-01 names "an authorized staff member" without a criterion that defines the authorization, and AC-02, AC-08, and AC-09 gate their writes on request identity and generation fences alone, so an authenticated caller who names another workspace's incident could append addenda to it, attach files to it, create exports of it, and read its entries through query and filter, while every identity, fence, and issuance criterion passed; incident records carry exactly the sensitive event-day accounts this spec exists to keep private.

    One input this criterion needs is not established by any approved artifact today and is not invented here. F-703 is PROPOSED and names no role set, so the permission above cannot be named. Until F-703 is approved this criterion is testable only as "every incident create, addendum append, attachment upload, export creation, retention or export action, and incident read is refused unless the acting actor holds an active membership of the workspace that owns the named incident's event, read server-side at that operation, and a refusal discloses nothing about whether that incident exists", not against a named role or permission identifier. Naming the incident write, read, and retention/export permissions with F-703 is an approval blocker below.

## Fixtures and Verification

- Planned automated fixture IDs are the acceptance IDs above; each must map one-to-one to a runnable test before approval can claim implementation readiness.
- F412-AC-02 includes the same concurrent retention-removal race as F412-AC-09, asserting exactly one winner in each direction and no addendum text appended when the removal wins.
- F412-AC-09 includes a concurrent fixture in which a retention removal and a standalone attachment upload race on one incident and exactly one wins: when the removal commits first the upload is rejected with no bytes stored, no attachment record, and no scan started, and when the upload commits first the removal covers it. It also includes a mismatched-reuse fixture in which a committed upload identity is re-presented for a different incident and is refused as a conflict.
- F412-AC-06 includes a fixture in which a member of the owning workspace who holds no attachment read permission is refused an attachment download URL while a permitted member is issued one, and a fixture in which that permission is revoked between two issuances and the second is refused while the first URL retains only its disclosed bounded validity until expiry.
- F412-AC-07 includes a fixture in which a member of the owning workspace who holds no incident export or download permission is refused the export stream and signed URL while a permitted member receives one, a fixture in which the permission is revoked between two issuances and the second is refused, and a fixture confirming that a URL issued before the revocation still resolves for its disclosed validity and that this bounded window is the documented limit of the control.
- F412-AC-10 includes a fixture in which an authenticated actor holding no membership of the owning workspace names a valid incident and is refused at create, addendum append, attachment upload, export creation, and query/filter read, with a response that does not distinguish absence from denial, and a fixture in which authority removed while a create, append, upload, or export is in flight fails that request rather than committing it.
- Regulatory fixtures: none; this feature does not define regulatory ground truth.
- Security-sensitive and cross-workspace paths require negative authorization tests; provider paths require success, duplicate-delivery, retry, invalid-signature, and permanent-failure tests where applicable.
