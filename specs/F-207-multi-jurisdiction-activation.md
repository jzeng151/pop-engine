# F-207 · Multi-Jurisdiction Activation

**Status:** PROPOSED (2026-07-26) — ready for review; not implementable until approved and listed in `docs/BASELINE.md`.

**Phase:** 4 · **Issue:** [#52](https://github.com/jzeng151/pop-engine/issues/52) · **Owner:** TBD · **Reviewer:** product owner · **Approval date:** —

## Purpose and User Outcome

PopEngine can activate a second approved jurisdiction by publishing data and fixtures through the existing generic engine, proving expansion does not require jurisdiction-specific executable code.

## Scope

**In scope**

- Publish one named second jurisdiction's intake registry, classifications/reference data, ruleset artifact, holiday calendar, primary sources, and executable fixtures.
- Select jurisdiction explicitly and evaluate through the same validated AST, engine, finding, and plan contracts.
- Preserve immutable per-jurisdiction artifact versions, checksums, changelog, approvals, and historical replay.

**Non-goals**

- A core-engine rewrite, jurisdiction package/calculator, named code branch, guessed regulatory fact, nationwide coverage, or mixed-jurisdiction plan.
- Adding a generic AST primitive inside this feature when the approved schema cannot express a required rule.

The publication-transition identity in `F207-AC-06` relies on it. ## Inputs, Outputs, State, Validation, and Errors

- Inputs are an approved jurisdiction key plus that jurisdiction's immutable artifacts; output is the normal engine plan with jurisdiction/ruleset/calendar provenance.
- Publication state is draft → verified/reviewed → tested → published; any unexpressible classification stops publication.
- Missing, conflicting, research-required, and coverage-gap states remain visible end to end and never become no requirement.
- Missing or unresolved material data stays visibly unset, unknown, pending, or failed as appropriate; it never becomes a successful or complete result.
- Invalid input produces a field or action-specific error without partial mutation. Retriable external failures preserve the user's confirmed state and expose a safe retry.

## UI and Accessibility

- Jurisdiction selection and plan banner name the active jurisdiction/artifact; unsupported locations stop with coverage guidance rather than falling back to NYC.
- The complete workflow is keyboard operable, uses programmatic labels and visible focus, does not encode status by color alone, and announces asynchronous success or failure.
- Empty, loading, permission-denied, validation, provider-failure, and unavailable states have explicit copy and a safe next action.

## Acceptance Criteria

1. **F207-AC-01:** The second jurisdiction publishes all required registry, classification, rules, calendar, source, fixture, version, checksum, changelog, and approval artifacts.
2. **F207-AC-02:** The engine passes every approved second-jurisdiction scenario and boundary fixture with deterministic byte-stable output. It is not unchanged today, and this criterion does not claim it is: `parseIntakeContract` in `packages/engine/src/intake/registry.ts` requires the NYC-only rule ids `SAPO-BLOCK-PARTY-ELIG-001` and `ADV-ALCOHOL-PUBLIC-001` (lines 56-57) and looks both up unconditionally when it builds the contract (lines 185-188), throwing `Intake contract invalid: ruleset does not publish <id>` when either is absent. A ruleset carrying only second-jurisdiction data therefore fails to parse before any evaluation runs. Satisfying the parser by adding those NYC ids to another jurisdiction's artifact is forbidden: it would invent a permit name, trigger, and source for a jurisdiction that never published them, which is exactly the regulatory invention `AGENTS.md` prohibits. The prerequisite in Approval Blockers must land first; until it does, this criterion is not runnable for a second jurisdiction and approving it as written would approve a criterion that cannot pass honestly.
3. **F207-AC-03:** The implementation adds no jurisdiction-named calculator, package, condition evaluator, or runtime branch.
4. **F207-AC-04:** If a required classification cannot be represented by the approved AST, publication stops and a separate architecture/schema decision is opened.
5. **F207-AC-05:** The checksummed current NYC v2.11 artifact (`rules/nyc-rules.v2.11.json`, sha256 `0f048ecc9a36794871ee8a81eb0d4d3b1519087dcf2d161a6c418de5ca555851`) and full scenario fixtures v7 remain unchanged and green; older NYC artifacts run only as explicitly versioned historical replay cases.
6. **F207-AC-06:** Every operation this feature defines is admitted by one of two authorities, both re-read server-side from stored state at the moment of the operation and never taken from the session or a client-supplied claim. Publishing a jurisdiction's artifacts through the draft → verified/reviewed → tested → published progression that F207-AC-01 requires complete, and stopping publication and opening the architecture/schema decision under F207-AC-04, are platform functions and are admitted only by the separate platform rules-admin role, on the terms `F703-AC-04` states for every such function rather than on a second formulation stated here, with the authority read inside the same transaction that commits each publication state transition, and never derived from a workspace role. Each of those state transitions is a durable write and carries a stable client-supplied request identity, committed with the transition under a uniqueness constraint scoped to the jurisdiction and the exact artifact set the transition advances, and resolved from its committed record before the transition is applied. A request presenting an already committed identity returns the outcome that request originally recorded and advances the progression no second time, so a lost response cannot move a jurisdiction's artifacts two steps along draft → verified/reviewed → tested → published for one administrator action, or open a second architecture/schema decision under F207-AC-04 for one stop. The acting actor's current authority is not one of the checks that identity is resolved past: the authority that admits a first attempt, membership and permission where an organizer acts and the equivalent admission where the caller is a public or door client, is re-read server-side at the replay, and the stored outcome is returned only if it still admits the request, so a replay presented after that authority is gone is refused and discloses no more than a first request would; the only exception is authority the committed operation itself removed, which `F411-AC-08` states once for this branch. That identity binds its operands under the rule `F411-AC-08` states once for every client-supplied identity on this branch, so a reuse naming a different jurisdiction, artifact set, or target state is refused as a conflict rather than being answered with the stored result. Jurisdiction selection, the engine evaluation reads it feeds (F207-AC-02), and the historical replay reads F207-AC-05 permits name the workspace that owns the event being evaluated and are admitted only by the acting actor's current F-702 membership of that workspace, re-read server-side from stored membership at each read; workspace membership admits no publication operation and the platform role substitutes for no membership check. A request failing either check is refused before any durable write and before any artifact, provenance, or plan data is disclosed, and its response does not distinguish a jurisdiction, artifact, or plan that does not exist from one the actor may not see. The check is at the operation and not at session start or workspace switch, so authority removed while a request is in flight causes that request to fail rather than commit.

   F207-AC-01 through F207-AC-05 all pass for a caller who holds no authority at all. They require the artifacts to publish completely, the fixtures to pass deterministically, the implementation to add no jurisdiction-named code, publication to stop on an unexpressible classification, and the NYC artifact to stay green, and not one of them asks who the actor is. The publication restriction was written only in the System Impact privacy row, which creates no acceptance criterion, so an implementation built to the criteria could let any authenticated user advance a second jurisdiction's artifacts through the publication states, and could let an organizer who names another workspace's event read its evaluation provenance and replay output.

   One input this criterion needs is not established by any approved artifact today and is not invented here. F-703 is PROPOSED and names no role set, and F-702 is PROPOSED and establishes no approved membership record, so neither the publication permission nor the membership check above can be named against an approved artifact. Until they are approved this criterion is testable only as "every publication operation is refused unless the acting actor holds the separate platform rules-admin role, and every organizer-side selection, evaluation, or replay read is refused unless the actor holds current membership of the owning workspace, each read server-side at that operation, with a refusal disclosing nothing about what exists", not against a named role, permission identifier, or membership record shape. Naming the publication permissions with F-703 is an approval blocker below.

7. **F207-AC-07:** Every publication state transition names the exact current publication state of the jurisdiction and artifact set it acts on, and commits only by compare-and-swap on that state inside the same transaction that applies the transition. That covers each step of the draft to verified/reviewed to tested to published progression F207-AC-01 requires complete, and it covers the stop that F207-AC-04 performs when a required classification cannot be represented by the approved AST, because a stop is a transition of the same progression and not an action beside it. A transition whose named current state is no longer the current one is rejected in full, advances nothing, opens no architecture/schema decision, publishes no artifact, and returns the current state for the administrator to re-read and decide again.

   The state a transition names is the position of that jurisdiction's artifact set in the progression, together with a monotonic value that changes on every transition of it. It is deliberately not any artifact's own version or checksum. F207-AC-05 and F207-AC-01 make the artifacts versioned and checksummed and this criterion leaves that untouched, but the artifacts do not change when the progression moves: two administrators who read the same tested artifact set hold identical checksums and versions before and after either of them advances it, so a comparison on artifact identity passes for both and detects nothing. The concept this criterion fences is the state of the publication process, which is the thing a transition mutates and the only thing whose staleness distinguishes a first attempt from a lost update.

   F207-AC-06 does not supply this. Its request identity is committed under a uniqueness constraint scoped to the jurisdiction and artifact set and binds its operands, so it recognises the retry of one administrator's own transition and refuses a reuse naming a different jurisdiction, artifact set, or target state. Two administrators acting from the same observed state send two distinct identities, which are not retries of each other, so both resolve to no committed outcome and both are admitted; the authority check finds the platform rules-admin role for each, because both genuinely hold it. This is the same distinction F208-AC-01 draws between a replay identity and the constraint that enforces a limit. Without the fence a stale advance can commit after a stop has already opened the architecture/schema decision under F207-AC-04, which publishes a jurisdiction whose classification the team has recorded as unrepresentable, and a stale stop can overwrite a progression that has already advanced, which reports a published jurisdiction as blocked and opens a second decision for one blockage. Either outcome is a regulatory publication state that no administrator chose, so it is a state that must not be reachable by two people doing exactly what the criteria permit.

   One input this criterion needs is not established by any approved artifact today and is not invented here. F207-AC-01 enumerates the artifacts a jurisdiction must publish and does not establish a durable record of the progression itself, so there is no approved place for the current state and its monotonic value to live, and this criterion names neither a storage shape nor a value type. Approving the jurisdiction registry and artifact layout is where that record belongs, and it is recorded as an approval blocker below. Until then this criterion is testable only as "two transitions composed against the same observed publication state, whether two advances, two stops, or an advance and a stop, commit at most one of them, and the loser is rejected without advancing, publishing, or opening a decision", not against a named state record or version field.

## Fixtures and Verification

- Planned automated fixture IDs are the acceptance IDs above; each must map one-to-one to a runnable test before approval can claim implementation readiness.
- F207-AC-06 includes a negative fixture per publication operation in which an authenticated actor holding no platform rules-admin role, including a workspace owner, is refused each publication state transition and the F207-AC-04 stop action with no transition committed; a fixture in which an actor holding no membership of the owning workspace names a valid jurisdiction, artifact, or plan and is refused selection, evaluation, and replay reads, each response indistinguishable from the one for a record that does not exist; and a fixture in which authority is removed while a publication transition is in flight and that request fails rather than commits.
- F207-AC-06 includes a fixture in which a publication state transition commits, its response is lost, and the retry presenting the same identity returns the original recorded outcome rather than advancing the progression a second time, and a mismatched-reuse fixture in which that committed identity is re-presented naming a different artifact set and is refused as a conflict, advancing nothing.
- Regulatory fixtures: A complete new jurisdiction suite with named scenario and below/at/above boundary IDs must be approved by the product owner under `docs/DOCUMENTATION-GOVERNANCE.md` §6, which is the whole requirement since second-party review was retired on 2026-08-05; NYC scenario fixtures v7 against the checksummed v2.11 artifact (`rules/nyc-rules.v2.11.json`, sha256 `0f048ecc9a36794871ee8a81eb0d4d3b1519087dcf2d161a6c418de5ca555851`) remain the current regression suite, with older versions labeled historical replay only.
- F207-AC-07 includes a fixture in which two platform rules-admins holding distinct request identities advance the same jurisdiction and artifact set from the same observed state and exactly one commits, a fixture in which a stop under F207-AC-04 commits first and a concurrent advance composed against the pre-stop state is then rejected without publishing, a fixture in which an advance commits first and a concurrent stop is rejected without opening a second architecture/schema decision, and a fixture proving the losing transition's rejection is distinct from the F207-AC-06 replay path, which still returns the original outcome for a repeat of the winner's own identity.
- Security-sensitive and cross-workspace paths require negative authorization tests; provider paths require success, duplicate-delivery, retry, invalid-signature, and permanent-failure tests where applicable.

## Rollout and Fallback

This spec treats publishing a jurisdiction's holiday calendar as a repeatable activation step, but it is unsolved for the FIRST jurisdiction: no located source establishes that an agency's published closure stops its filing counter, and NYC's own rules span a city agency and a state agency whose staff calendars differ (`apps/api/src/calendar.ts`). A second jurisdiction cannot be activated by a procedure that has never been executed once. Whatever resolves #130 defines the procedure this spec would repeat.
- Approve F-702 and F-703, and name with F-703 the publication permissions `F207-AC-06` checks. That criterion checks a permission no approved artifact defines today and may not invent one, so until F-703's matrix names them the publication leg is testable only at the check-shape level stated there, and until F-702 is approved the organizer leg is testable only at the membership level stated there.
